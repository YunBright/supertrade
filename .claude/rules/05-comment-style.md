# 注释规范

注释是**给下一个读代码的人(含 AI)用的**。目标:一次读懂契约与边界,不用翻 git log。

## 写什么

1. **契约**:这个函数保证什么、返回什么形状、什么情况下不返回。
2. **边界**:哪些输入被拒、哪些状态不允许、哪些顺序不能改。
3. **失败形态**:出错时长什么样(状态码 / code / 是否静默)。**"静默失败"必须写出来** ——
   它是最容易在生产里咬人的一类。
4. **非显然的理由**:只写一句,写"为什么是这个"而不是"这个是什么"(代码已经说了)。

## 不写什么

- 调试经过 / 挖坑填坑的过程("原来是…后来改成…"、"本轮改造前的真实故障")。
- 贴生产错误原文、日志片段、实测行数(31371 行 / 23837 行 / 4130 个会员)。
- 日期流水账("2026-10-21 新增:"、"2026-10-22 修复")—— git log 有。
- 已删功能的墓碑注释(函数已删、端点已删,留一句"已删除"没有读者需要)。
- 复述代码就能看懂的话。

## 长度

| 场景 | 上限 |
|---|---|
| 函数头一行注释 | 1 行 |
| 边界 / 警告块 | 2–8 行 |
| 包头注释 | ≤ 15 行 |

超过 8 行 ⇒ 说明该拆:规则留在一处,别处一行指过去。

## 反例 → 正例

```go
// ❌ 40 行:事故经过 + 实测数字 + 改造史 + 规则
// ⚠️ 2026-10-26 门店反馈:之前这里没校验 ⇒ 客户端传 {"items":[…]} ⇒
// 症状是"保存成功了,读回来却没变" —— 最难查的那种。
// 根因是反序列化字段名写错时得到空列表,而空列表被当成"没有变更"。

// ✅ 2 行:规则 + 一句理由
// ⚠️ 空 openings 一律 400(字段名写错时反序列化会得到空列表,
// 静默写入等于"保存成功但没变")。
```

## 写完自查

- 这条注释删掉,会不会有人踩坑?会 ⇒ 保留(压到 2–6 行)。
- 这条注释删掉,会不会有人看不懂代码?不会 ⇒ 删掉。
- 有没有别的文件在讲同一件事?有 ⇒ 本处留最关键的那一句,不要复述全文。
