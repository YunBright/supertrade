# POS 收银待开发功能文档

**版本**：V1.0（2026-10-31）
**来源**：超市流水对账系统一期（`docs/超市流水对账系统.md` FR-01/FR-03/FR-04）在实现时发现的**收银流水字段缺口**。
**用途**：把"对账系统需要的、但收银侧当前给不出的"字段逐项记录成 POS 的待开发需求，
并写明本期（cash-recon 一期 MVP）采用的**临时处理方案**，避免研发侧用"看起来对"的近似值埋掉差异。

---

## 1. 现状：两个收银流水源

对账系统遵循需求文档的架构约定：**门店有 cube 源查 cube，无源查本地 PG**（`cubesource.Decide` 三态：
cube / 本地 PG / 链路故障 → 503，**不回落**）。

| 源 | 位置 | 可用字段 | 用途 |
| --- | --- | --- | --- |
| cube `payflow` | 语义层 model `payflow`，源表 `t_rm_payflow`（`storage: live`） | `branch_no`、`paid_at`、`pay_way`、`pay_amount`、`cashier_id` | 有 cube 源的门店 |
| 本地 PG `pay_flows` | `internal/transaction/model/model.go`（表 `pay_flows`） | 见下：`order_no`、`random_order_no`、`source_branch_no`、`sale_way`、`pay_way`、`pay_way_name`、`pay_amount`、`card_no`、`vip_no`、`cashier_id`、`cashier_name`、`counter_no`、`salesman_id`、`paid_at` | 无 cube 源的门店 |

两个源**共同缺**的字段（本期全部按"缺口"处理，不做猜测性填充）：

1. **班次号 `shift_no`** —— 无法按班次做长短款。
2. **结算批次号 `settle_batch_no`** —— 无法做"结算批次 ↔ 收银批次"的强匹配。
3. **单据类型（销售/退款/充值/储值消费）** —— 只能靠 `pay_amount` 正负推断"是否冲销"，推断不了"是什么业务"。
4. **平台渠道标识（美团/抖音/饿了么/团购）** —— 只知"微信/支付宝收款"，不知"来自哪个平台结算"。
5. **支付方式字典（`pay_way` 的稳定枚举）** —— 两侧都只存裸编码/名称，没有受控字典与"维度归属（现金 / 微信 / 银行卡 / 储值 / 挂账 / 找零）"的权威映射。

## 2. 逐项缺口与本期临时方案

### 2.1 班次号（FR-04 长短款）

- **缺口**：cube `payflow` 无 `shift_no`；本地 `pay_flows` 也无。cube `sale_detail` 有 `shift_no/pos_id`，但它的粒度是**商品明细行**，不能直接当收银流水用。
- **本期方案**：长短款维度降为「**门店 + 业务日 + 收银员**」；班次字段在台账里固定写 `ALL`，并在差异工作台注明"该门店无班次口径"。
- **影响**：同一天同一收银员多个班次时，长短款只能按日汇总，无法定位到具体班次。
- **POS 待开发**：`payflow` / `pay_flows` 增补 `shift_no`（与 `sale_detail.shift_no` **同一套编码**），并保证交班时同一班次的收款行可完整归档。

### 2.2 结算批次号（FR-03 匹配规则 2）

- **缺口**：两侧都没有批次号。因此需求文档里的"结算批次号与收银系统批次号匹配"**在一期无法实现**。
- **本期方案**：匹配主键降为「**渠道 + 业务日 + 净额**」，T+N 容忍天数由规则配置（默认 1，上限 7）。批次号匹配标记为未实现。
- **影响**：同一渠道同一天有多笔结算批次（如平台分次打款）时，只能靠金额/时滞匹配，可能配错对。
- **POS 待开发**：`payflow` / `pay_flows` 增补 `settle_batch_no`（渠道侧结算批次号）；若渠道不提供批次号，则提供**收银批次归档号**（闭店批次），由 POS 在闭店时生成。

### 2.3 单据类型

- **缺口**：无 `doc_type` / `biz_type`。
- **本期方案**：只用 `pay_amount` 的符号判断正负（负数 = 冲销大于收款），聚合时按净额处理；**不区分**销售、退款、储值充值、储值消费。
- **影响**：支付方式分析里"退款"和"负向调整"合并成一类，无法单独看退款率。
- **POS 待开发**：`payflow` / `pay_flows` 增补单据类型枚举（至少：销售 / 退款 / 储值充值 / 储值消费 / 调整），并保证与 `pay_amount` 符号自洽。

### 2.4 平台渠道来源

- **缺口**：只知支付方式（微信/支付宝/银行卡），不知"这笔钱最终由哪个平台结算"（美团/抖音/饿了么/团购）。
- **本期方案**：渠道流水导入时由出纳**手工选择渠道**（银行账户或平台账户）；匹配只按"渠道 + 日期 + 金额"，不反查收银侧的平台标识。
- **影响**：平台结算单与收银流水之间缺少机器可校验的关联键，平台差异只能靠金额与时滞。
- **POS 待开发**：收银流水增补"结算渠道 / 平台编码"，与渠道结算单的 `channel` 使用**同一套编码**。

### 2.5 支付方式字典（需求文档架构约定：支付方式分析以 cube 源为准）

- **缺口**：`pay_way` 是裸编码，cube 与本地 PG 各存一套；没有"受控字典 + 维度归属"的权威来源。
- **本期方案**：以 **cube 源**的 `pay_way` 取值为基准做映射（现金 / 微信 / 银行卡 / 储值 / 挂账 / 找零），映射表落 `recon_rules`（按门店可覆盖）；**映射不到的值一律进 `unmapped_pay_way` 差异**（不静默归到"其他"，也不计入匹配率分母）。
- **影响**：新增支付方式（如数字人民币）时，在补映射前会持续产生 `unmapped_pay_way` 差异 —— 这是**故意的**：让口径缺口可见，而不是被平均掉。
- **POS 待开发**：发布 `pay_way` 字典（编码 / 名称 / 维度归属 / 是否计入现金实盘 / 是否参与银行匹配），并保证新增支付方式时同步登记。

## 3. 对账系统侧的对应约束（供 POS 联调时核对）

1. **收银流水不落 cash-recon 库**：实时查（cube / 本地 PG），只在审核计算（freeze）时快照到 `recon_cash_flows`。
2. **cube 查询防慢查询**：按业务日**逐日**查询，过滤条件只用 `paid_at`，按 `业务日 × pay_way` 聚合，单次区间 ≤ 31 天，超时 30s fail-fast（503，不回落）。
3. **现金与找零不参与银行匹配**：现金实盘走长短款流程；`change`（找零）不计收款，不进匹配率分母。
4. **手续费永远单列**：渠道结算单上的手续费单独入库，不允许把"到账金额 = 应收金额"凑平。

---

## 4. 验收口径（POS 补齐字段后）

- 任一日任一门店，可按「班次」输出收款合计，且与闭店报表逐项一致。
- 渠道结算批次号可与收银批次号一一对应（或明确一对一/一对多关系）。
- 退款、储值充值/消费可单独统计，且与 `pay_amount` 符号自洽。
- 平台结算单能凭"平台编码 + 批次号"定位到收银侧流水，不再只依赖金额与时滞。
