## 1. 为什么要做

门店对毛利看板的原话（2026-10-29）：

> 部位明细卡片，每个部位的进货列数值分上下两行，上面是建议分割（AI/算法），下面是实际分割。
> 去掉应有列和差异列（因为进货是参考的分割，两列数据没有意义）。
> 统收合并到销售；营收为该部位当日的销售汇总数 + 统收金额。
> 销售成本要按「建议分割 vs 实际分割」重新算。

拆开看是三件事：

1. **「进货」这一列从"事实"降级成"参考"** —— 它不再代表账面入库量，而是**今天切了多少**的两种看法（算法建议 vs 实际）。⇒ 依赖「进货」的「应有 / 差异」两列随之失去意义。
2. **统收不再单列** —— 统收（酒店大宗出库）本来就是销售，拆成两列门店要自己加。⇒ 合并进销售/营收，但**必须能看见它有多少**（角标 + 气泡）。
3. **销售成本要用分割权重算，而不是用"进货"这个混合值算** —— 现在的入库量是「实录 pig_cuts → 统计基线 p50 → LLM → 袋子兜底」四级兜底出来的混合值，门店看不懂它到底是哪一种。

## 2. 三个数（按部位）

| 记号 | 名字 | 含义 |
|---|---|---|
| `S_c` | **建议分割** | **AI/算法**建议今天切出该部位多少 kg |
| `A_c` | **实际分割** | 今天该部位**实际**被切出/消耗掉多少 kg |
| `W_c` | **调整后权重** | 参与**成本计算**的分割权重（= 建议分割，或按重分配规则调整过的建议分割） |

### 2.1 建议分割 `S_c`

逐猪、逐部位累加，来源优先级：

1. **统计基线 p50**（`pig_forecast_baselines`，按**体重段 × 部位**分层，样本数 ≥ `MinForecastSamples`=5 才可用）
2. **LLM 建议**（`whole_pigs.llm_advice_json` 的 `cuts[].expected_kg`）—— 基线没有的部位才用它

⚠️ **不含 `pig_cuts` 实录**。理由：owner 明确「建议分割（AI/算法）」与「实际分割」是**两行**，实录属于「实际」那一侧。

⚠️ 原建议分割**永远保留**（它是"整日的建议"），调整后的权重是**另一个数**（`adjusted_split_kg`）。

### 2.2 实际分割 `A_c`

**来源二选一**，来源标记 `actual_split_source`：

- `recorded` —— 当日 `pig_cuts` 里该部位的 `weight_kg` 之和（**实录优先**；`cube_product_id` 为空的补录也要算，按 `cut_type` 归集）
- `derived` —— 没有实录时按下面的公式倒推

#### 有日终实盘（`data_source == actual`）

```
A_c = 全店期末结余_c + 销售_c + 统收_c + 报损_c − 全店期初_c
     其中 全店期末结余_c = 猪肉台实盘_c + 冷库量_c
```

⚠️ **"实盘"在全仓只有一个含义：当日猪肉台上盘出来的数**（盘点单 `actual_remain_kg`，**不含冷库**）。
**冷库量是盘点单里的另一个字段**（`cold_store_kg`），报表上**单独一列**，**不是实盘**。
⇒ 所以上面那一项叫「**全店期末结余**」，不叫「全店期末实盘」。

这是**全店恒等式**解出来的「今日新分割产出」：

```
期初 + 今日分割 − 销售 − 统收 − 报损 = 期末
```

⇒ **搬上台是冷库→台面的内部转移，在全店口径里天然抵消** ⇒ **搬上台的老货不会被算成今日分割**（这是 owner 特别点名的坑）。

**为什么不能用台面口径**：台面恒等式里**根本没有"今日分割"** —— 今天的分割先进冷库、再搬上台，台面只看得到"搬上台"：

```
台面期末 = 台面期初 + 搬上台 − 搬回 − 销售 − 统收 − 报损
```

⇒ 从台面**推不出**今日分割 ⇒ 要算"今日新分割"**必须**用全店口径 ⇒ **必须把冷库量加回来**。

#### 无日终实盘

```
A_c = max(0, 销售_c + 统收_c + 报损_c − 全店期初_c − 搬上台_c)
```

⚠️ 这是**台面流量倒推的近似**，**口径不精确**：台面流量里推不出"今日分割"（今日分割先进冷库、再搬上台），只能拿"消耗 + 搬上台"反推。冷库压货多的部位会**偏保守**（偏小）。代码里必须写明这是近似。

#### 显示规则（后端负责置 null，前端只按 null 渲染空）

- `recorded` ⇒ **总是给值**
- `derived` 且**有完整日终盘点** ⇒ **总是给值**
- `derived` 且**无完整日终盘点** 且 `A_c < S_c` ⇒ **给 null**（owner：「实际分割小于建议分割时显示为空」，且这条只在无实盘时生效）

### 2.3 调整后权重 `W_c`（成本基准）

```
O = { c : A_c > S_c }              # 用**内部** A_c（含被隐藏成 null 的那些）
if O 为空:
    W_c = S_c                       # 含"实际分割全为空"的情形
else:
    E = Σ_{c∈O} (A_c − S_c)
    for c ∈ O:  W_c = A_c
    for c ∉ O:
        第一轮（按可压缩量）:  pool_c = max(0, S_c − A_c)
            take_c = min(pool_c, E × pool_c / Σpool)
            W_c = S_c − take_c
        第二轮（不够，按建议比例摊）:
            take_c = min(W_c, rest × W_c / ΣW)
            W_c −= take_c
```

⇒ **总量守恒**：`Σ W_c == Σ S_c`（守不住时记告警）。

## 3. 两条守卫（防"短卖被掩盖"）

| 守卫 | 触发 | 行为 | 理由 |
|---|---|---|---|
| ① 没进猪不重分配 | `Σ S_c <= 0` | `W_c = S_c`（全 0） | 当天没有进猪 ⇒ 没有建议 ⇒ 任何重分配都是拿"销量"冒充"分割"，会把**账面短卖**掩盖成 0 |
| ② 无处可挪不重分配 | `poolTotal == 0` | `W_c = S_c` 不变 + **告警** | 同上：把短卖撑成 0 等于把损失藏起来 |

⚠️ 生产实测（branch 00 / 2026-10-29，`belly`）：

```json
{"opening_kg":"0","purchased_kg":"0","sold_kg":"27.5813","expected_remain_kg":"-27.5813",
 "sales_cost_yuan":"0","cost_incomplete":true}
```

没有进猪 ⇒ `S_belly = 0` 而 `A_belly = 27.58` ⇒ 若不守卫，五花会被撑到 `W = 27.58` ⇒ `expected_remain_kg` 从 **−27.58（账面短卖，红字告警的来源）** 变成 **0** ⇒ **短卖被抹掉**。守卫①/② 就是防这个。

## 4. 成本引擎怎么接

部位移动加权（`cut_cost.go` 的逐部位循环）：

```
availKg = 期初_c + W_c            # ← 入库量换成 W_c（原来是 ProducedKg 混合值）
availAmt = 期初金额_c + 入库金额_c
movingAvg = availAmt / availKg
```

⚠️ **入库金额不能跟 kg 同比缩放** —— 那样单价不变、毛利不变，等于没做。
⇒ 当日可摊猪成本**按 `W_c` 的比例重新分摊**到各部位（总额不变，比例变 ⇒ 单价才会变）。

⇒ **对账恒等式仍然闭合**：`salesCost = availAmt − closeAmt − bulkCost − wasteCost` 是代数恒等式，改 `prodK` 不破坏它 ⇒ `reconciliation.diff_yuan` 仍为 0。

⚠️ `ExpectedClosingKg`（全店口径的「应有」）会随 `W_c` 变 —— 它是**内部**字段（成本引擎 + 账面短卖告警用），**不动**。

## 6. 「实盘剩余」口径变更（2026-10-29 owner 口径）

`actual_remain_kg`（报表的「实盘剩余」）从「引擎期末（全店结余，含冷库）」改成 **「该部位当日的柜台(猪肉台)实盘」**。

- 数据源：当日**完整盘点单**的 `cuts` JSONB 里该部位 `CutSnapshot.ActualRemainKg` 之和（`CutSnapshot.ActualRemainKg` 的定义就是台面数，冷库另给 `ColdStoreKg`）。
- 连带：`expected_remain_kg` 同步换成**柜台口径** = 全店应有 − 冷库量 ⇒ `variance_kg = actual − expected` **数值不变**、语义自洽。
- ⚠️ 引擎内部的 `CutDailyCost.ExpectedClosingKg`（全店口径）**不动**（成本链 + 账面短卖告警靠它）。
- ⚠️ **实现上的取舍（已落代码 + 有单测锁住）**：`expected_remain_kg` 的口径切换**只在有完整盘点时**做。
  没有盘点单时冷库量只能退回**引擎链值**，而链值**不含今天切出来的量**（今天的分割先进冷库、没搬上台就不在链里）
  ⇒ 拿它一刀切地去减，会算出「今天的分割已经摆上台面了」的假数（实测 19.23 被算成 10）。
  ⇒ 没有柜台读数可比时，`expected_remain_kg` 保持**全店口径**（与引擎期末一致 ⇒ 链的连续性不破）。
  ⇒ `cold_store_kg` 本身**照旧**退回引擎链值（owner 口径），只是不用它去减「应有」。

## 7. 前端口径

- 表格列（11 列）：`部位 | 期初 | 进货 | 销售 | 报损 | 实盘剩余 | 冷库单价 | 营收 | 销售成本 | 毛利 | 毛利率`
- **进货列上下两行**：上行 = 建议分割（弱化显示，这是"参考"）；下行 = 实际分割（null ⇒ 不显示数字）
- **统收列删除**：合并进销售（kg）与营收（元），右上角感叹号角标 + 气泡（鼠标悬浮 / 触屏点击）
- **应有 / 差异列删除**（后端字段保留：对账卡、短少提示、告警还在用）
- 窄屏卡片与宽屏**字段完全一致**
- `derivedRemainKg`（前端自算的账面推演）要**减去 `cold_store_kg`**，否则与柜台口径的 `expected_remain_kg` 对不上 ⇒ "应有被修正"的角标会每行误报
  - ⚠️ **只在 `actual_remain_kg` 有值时**（= 有完整盘点）才减：没有柜台读数时后端的 `expected_remain_kg` 保持**全店口径**（见 §6 的实现取舍）⇒ 一律减会把非盘点日的"应有"减出一个假差额。

## 8. 已知局限（**上线前必须知道**）

⚠️ **生产上两个门店（00 / 01）根本没有鲜肉的录猪/盘点数据**（2026-10-29 实测）：

| 表 | 00 | 01 |
|---|---|---|
| `whole_pigs` | 0 | 0 |
| `pig_cuts` | 0 | 0 |
| `pork_cuts_stocktakes` | 0 | 0 |
| `waste_logs` | 0 | 0 |
| `pig_forecast_baselines` | 0 | 3（**样本数都 < 5，不可用**） |
| `counter_loads` | 1（2026-10-02） | 0 |

⇒ 后果：

1. **`S_c` 恒为 0**（没进猪 ⇒ 没建议）⇒ 「建议分割」这一行在生产上现在是 0。**这不是代码问题，是门店没在用第①步「录猪」**。
2. 守卫① ⇒ `W_c == S_c == 0` ⇒ **成本数字与改造前完全一致**（不会变差，也不会因为这次改动变好）。
3. 「实际分割」= `derived`（无实录）⇒ 无实盘时按台面流量倒推。
4. `cost_incomplete = true` 与「毛利 100%」的老问题**依旧存在** —— 根因是**没有成本来源**。

⇒ **让毛利真正算准的最短路径**（本次**不在**范围内，另行决策）：思迅日汇总表 `t_rm_daysum` 有 **`cost_price`**（cube `sales_report` model 已映射），`cost_price × 当日净销量` **直接就是销售成本**，不依赖本系统的录猪 + 移动加权链。
