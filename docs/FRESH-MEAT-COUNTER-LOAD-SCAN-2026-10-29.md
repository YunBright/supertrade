# 鲜肉 · 搬台「已录列表 / 改删 / 扫码录入」设计与口径（2026-10-29）

> 线1：**鲜肉 → 每日工作 → 搬台**
> 门店原话：
> 1. 「搬台无法看到已录列表，找不到修改，删除入口。」
> 2. 「搬台增加『从图片识别打称标签读取商品货号和重量并转化为部位和重量』的**扫码录入**功能。」
>    —— 澄清后 owner 改口：「**直接用条形码扫码即可获取到打称条形码里的数据了**」

---

## 0. 结论先写

| 项 | 结论 |
|---|---|
| 扫码要不要 AI 识图 | **不要**。打称标签上本来就有条形码 ⇒ 纯前端解析，不加后端接口、不用 LLM、不加依赖 |
| 货号怎么认 | **前缀锚定**：条码最左边就是货号，在「本店已知货号集合」里取**最长命中** |
| 重量怎么解 | **版式枚举 + 物理自洽校验**（重量 × 单价交叉验证）；**解不出就手输，绝不猜** |
| 后端要改吗 | **不要新端点**。`GET/PUT/DELETE /stock/counter-load` 早就存在，缺的只是前端 UI 与 repo 方法 |
| 仍缺的输入 | **owner 给一条真实打称条码**（见 §5） |

## 1. 后端（supertrade）

### 1.1 已有能力（不新增端点）

| 端点 | 用途 |
|---|---|
| `GET /stock/counter-load` | 当日搬台流水（已录列表的数据源） |
| `PUT /stock/counter-load` | 改某一行的重量（`qty_kg` 必填且 > 0） |
| `DELETE /stock/counter-load` | 删掉某一行的搬台记录 |
| `POST /stock/counter-load` | 提交搬台（前端「提交搬台」按钮走它） |

### 1.2 本次唯一的后端改动

`internal/fresh-meat/service/counter_load.go` 的 `CounterLoadLineView` 补两个字段：

- `cut_type` —— 该行属于哪个部位（**搬台界面要按部位显示**）；
- `cube_product_name` —— 商品名（扫出来/已录的行都要看得懂是哪个货）。

⚠️ 老数据的 `counter_loads.cut_type` 可能为空 ⇒ 列表侧按 SKU 反查部位映射兜底（已有逻辑）。

### 1.3 为什么「改货号」不是编辑项

`PUT` 只能改 `qty_kg`：**改货号 = 撤销这一行 + 重录一行**（成本链按行记账，货号变了就是另一批货）。沿用既有设计，不在本次扩大。

## 2. 前端（tradewind_app）

### 2.1 已录列表

- 新增 `lib/ui/fresh_meat/stock/counter_load_recorded_section.dart`
- 显示：部位 / 货号 / 重量 / 来源（整袋搬 vs 扫码搬）/ 标签号；
- 没有流水 ⇒ 给一句人话（「今天还没搬过台」），不空白。

### 2.2 修改 / 删除入口

| 操作 | 交互 | 调用 |
|---|---|---|
| 改重量 | 弹数字输入（**预填当前重量**）⇒ 确认 | `PUT /stock/counter-load` |
| 删除 | 二次确认 | `DELETE /stock/counter-load` |

- 后端 400 的 message **原样透给用户**（例：`qty_kg 必须 > 0`）。

### 2.3 扫码录入

```
扫码枪/相机 → 原始串
   ↓
WeighLabelBarcodeParser.parse(raw, knownSkus: 本店已知货号)
   ↓
解不出来 ──────────────→ 手工确认（选货号 + 填重量）
   ↓ 解出来
货号在今天的冷库清单里？
   ├─ 否 → 提示「不在今天的冷库清单里」（搬台只能搬冷库里有的货）⇒ 不加入
   └─ 是 → 确认卡（部位/名称/货号/**标价**/**单价**/重量，重量可改）
              ↓ 确认
        重量**累加**到该 SKU 的待搬输入 ⇒ 顶部提示「已加入待搬列表」
```

⚠️ **扫码不直接提交**：最终仍走面板底部那个「提交搬台」按钮 ⇒ 门店还能改。

## 3. 条码版式：为什么不能拍脑袋定

### 3.1 已知 / 未知

| 已知 | 未知 |
|---|---|
| 货号 = **5 位数字串**（`01409` 五花肉 / `01402` 精选腩排 / `01500` 猪尾骨…，取自生产库 `branch_cut_mappings`） | 重量位**占几位** |
| 货号在条码的**最左边** | 校验位占几位 |
| 顺序 = 货号 + 重量 + 校验 + 价格 | 价格位占几位、单位是「元」还是「分」 |

⚠️ owner 只说过「条码 = 货号 + 重量 + 校验 + 价格」和「扫条码就能拿到数据」，**没有给过一条真实条码**。
⚠️ 版式猜错的代价很贵：**重量差 10 倍**（12.345 kg 读成 1.234 kg ⇒ 账面直接错 10 倍，门店还看不出来）。

### 3.2 做法：枚举 + 物理自洽

1. **枚举版式**（`buildWeighLayoutCandidates()`）：
   重量位宽 {5,6,4} × 校验位宽 {1,0} × 价格位宽 {4,3,5} × 重量单位 {整克, 2 位小数}，
   按「整克 → 有校验位 → 价格 4 位 → 重量 5 位」排序；
2. **总位数必须精确匹配**（条码是定长的 ⇒ 多一位少一位都判不成立）；
3. **物理校验**（全部满足才采用）：
   - 重量 ∈ [0.02 kg, 30 kg]（像"一袋肉"）；
   - 标价 ∈ [0.5 元, 1000 元]；
   - **单价 = 标价 ÷ 重量 ∈ [3, 150] 元/kg**（猪肉部位的正常区间）。
4. **一个都过不了 ⇒ 不给重量**（`weightKg == null`）⇒ 门店手输。

⚠️ **单价交叉验证是关键**：重量位错一位 ⇒ 重量差 10 倍 ⇒ 单价也跟着差 10 倍 ⇒ 立刻被区间挡掉。
（判别力用例：条码 `货号+001500+校验+3990` 按"固定取前 5 位"会读成 0.15 kg，
单价 492 元/kg ⇒ 被挡 ⇒ 落到 6 位版式 1.5 kg。）

### 3.3 失败模式是「响亮」的

| 情况 | 表现 |
|---|---|
| 货号不在本店已知集合 | 提示 + 走手工确认（不猜） |
| 货号认得、重量解不出 | 走手工确认（选货号 + 填重量），**不填 0** |
| 货号认得、但不在今天冷库清单 | 提示「不在今天的冷库清单里」⇒ 不加入 |

### 3.4 门店能肉眼核对

确认卡把**标价**和**单价**一起摆出来：

```
部位：五花肉
名称：五花肉
货号：01409
标价：39.90 元
单价：26.60 元/kg
条码：014090150073990
重量（kg）: [1.5]
```

⇒ 解析器的版式是假设 ⇒ **给门店一个能对账的数字**，比"悄悄给一个可能差 10 倍的数"安全得多。

## 4. 数据流与后端边界

- 扫码解析**全在前端**（纯 Dart，`lib/domain/fresh_meat/weigh_label_barcode.dart`）⇒ 规则可单测、不发请求、不碰数据库；
- 已知货号集合来自**当前冷库清单**（`StockSnapshot.lines[].cubeProductId`）；
- ⚠️ **不依赖 `product_barcodes` 表**：那张表里没有 00/01 门店的条码（只有 branch 10 的 155 条，其中 2 条是另一套 8 位货号体系）⇒ 扫码靠「已知货号集合 + 前缀锚定」。

---

## 5. 还缺 owner 一条真实条码

拿到一条**真实打称标签**（扫码枪扫出来的那串数字）后：

1. 核对 `buildWeighLayoutCandidates()` 的排序（若实际是「6 位整克」等，把那一项提前）；
2. 核对 `kWeighMinUnitPriceYuan` / `kWeighMaxUnitPriceYuan`（若本店的部位价格超出该区间）；
3. 核对「价格按分解」的前提（若标签价格是「元」）。

⇒ **改动集中在一处**，不需要翻 UI。
