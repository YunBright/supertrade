# AI 销售日报 / 周报 / 月报 — 产品需求文档

- 日期：2026-10-16
- 状态：已定稿（4 项关键架构决策已确认）
- 作者视角：零售业经理（业务真实性）+ 软件产品经理（边界与权衡）

---

## 0. 一句话

给单店店长一份**能直接指导今天补货、淘汰、调价**的推送，
而不是一张只有金额的表格；并且**每句结论都能追溯到它依据的数据**。

---

## 1. 业务视角：零售业经理真正要回答的问题

### 1.1 店长早上 8:50 打开群，最想知道什么

不是"今天卖了多少"——这个他盯 POS 就知道了。他要回答的是**接下来做什么**：

| 优先级 | 问题 | 需要的判断 |
|---|---|---|
| P0 | 昨天哪些商品**卖不动**了？是真的卖不动，还是**根本没货**？ | 缺货归因 |
| P0 | 哪些商品昨天**卖爆了但现在没货**，今天必须补？ | 断码预警 |
| P1 | 哪个**品类**在增长，为什么？（促销？天气？季节？） | 增长归因 |
| P1 | 哪个**供应商**的单品质量最好/最差？ | 供应商评估 |
| P2 | 昨天整体是涨了还是跌了，是不是正常波动？ | 可比性判断 |

### 1.2 「销量下降」至少有四种完全不同的原因（这是本产品的核心价值）

一个商品昨天销量跌了 60%，店长的动作**完全不同**：

| 原因 | 表面现象 | 正确动作 | 错误动作 |
|---|---|---|---|
| **缺货** | 销量跌 + 当前库存 ≈ 0 | 紧急补货 | 判定为滞销，砍掉订货 → **永久失去一个爆款** |
| **整体下滑** | 同品类全跌，且有货 | 检查是天气/客流/竞品 | 归咎于单品 → 误砍 |
| **品类正常轮换** | 该品类整体稳定，该单品独跌 | 考虑换供应商 / 下架 | 补货一个没人买的品 |
| **主动控量** | 有库存但销量平稳，库存高 | 可能是有意控量保价 | 误判为滞销 |

**所以本产品的第一价值不是"生成文字"，而是"归因正确"。**
一个把缺货说成滞销的日报，比没有日报更有害——它会导致真实的经营损失。

### 1.3 可比性：不做对比的数字没有意义

日报拿今天跟"一个普通周二"比毫无意义。必须注入上下文：

- **星期**：周五晚 + 周六是商超黄金档，周一是大谷底
- **法定节假日 + 调休**：`2026-10-01~08` 国庆，`2026-09-25` 中秋调休上班
  （**调休上班的周六是"工作日"，不是休息日** —— 这一条错了整份日报的对比基准就错了）
- **天气**：`下雨占营业时段多少` 显著影响生鲜和客流；
  高温影响冰饮冷饮、凉菜；寒潮影响取暖用品
- **门店上下文**：单店，不能与其他门店混比

**判定规则**：当"昨天"与"前天"在星期/节假日性质上不可比时，
日报**必须显式声明**「本期与上期可比性有限」，而不是给一个误导性的环比百分比。

### 1.4 毛利：数据不够就不显示（沿用既有铁律）

实测 `hbposv10` 成本覆盖率仅 25.3%。按 cost=0 算会显示"毛利率 100%"——
比不显示更坏，因为看到的人会据此判断"这个品类在赚钱"。

**本产品继承该铁律**：覆盖率不足时整块隐藏并说明原因，绝不显示假数。
这一条对 LLM 尤其重要 —— **必须把覆盖率作为硬约束写进 prompt**，
否则模型一定会给出一个"看起来合理"的毛利率。

## 2. 产品经理视角：边界与权衡

### 2.1 已确认的四项架构决策

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| 1 | LLM 归属 | **新建 `supertrade-sales-insight`** | sales-agg 现有注释明确"不发消息、不存业务数据"；新服务可独立升级而不动既有契约 |
| 2 | 数据喂法 | **预聚合事实包** | token 可预测、可审计、**结构上不可能拉全量** |
| 3 | 跨期上下文 | **注入上期结论摘要**，长度硬上限 | 环比既需要数字也需要叙事；摘要单独存 state，不累积 |
| 4 | 外部数据 | **内置节假日表 + 天气 API（失败降级）** | 节假日零依赖；天气降级为"未知"并标注 |

### 2.2 为什么"事实包"而不是 function calling（重要权衡）

用户设想"提供查排行榜的 function，让 LLM 自己调"。我建议**否决**这条路：

| 维度 | 事实包 | function calling |
|---|---|---|
| token 可预测性 | ✅ 固定，随配置线性增长 | ❌ LLM 可能调 1 次也可能调 20 次 |
| 延迟 | ✅ 1 次查询 | ❌ 5-10 轮串行 |
| 审计 | ✅ prompt 全文可存可查 | ❌ 需存完整 trace |
| 拉全量的风险 | ✅ **结构上不可能** | ❌ 模型判断失误就会 |
| 灵活性 | ❌ 加指标要改代码 | ✅ 即插即用 |

**结论**：LLM 的价值在"**解读**"，不在"查询"。查询交给确定性的代码，
LLM 只做归因与叙述。这也符合已有的
`sales-agg` 设计（`CubeQuerier` 窄接口 + 纯函数 `BuildSalesReportQuery` 便于断言）。

**保留的扩展位**：事实包结构带 `data_sufficiency` 标记，
未来真需要补查时可加 function，而不用重构。

### 2.3 Token 成本控制

- 事实包**硬上限**：Top N 默认 10，可配 1-20
- 上期摘要**硬上限**：默认 600 字符，超出截断并标记 `truncated: true`
- 发送前**长度自检**：超过阈值（默认 12000 字符）拒绝发送并告警，
  避免一个配置失误把 token 成本打上去
- 每次推理记录 token 用量，供后台统计

### 2.4 降级链（LLM 不可用时必须有东西）

```
LLM 正常     → AI 结论 + 事实数据
LLM 失败     → 规则版结论（环比/排行/缺货纯计算）+ 明确标注「规则模式」
取数失败     → 说明卡（沿用现有行为：群里什么都没发生最难查）
```

**规则降级不是失败**，是一个**可用但诚实**的产品形态：
日报的价值 60% 在数据，40% 在叙述。数据在就不该让整个推送停摆。

## 3. 功能需求

### 3.1 三种周期

| 周期 | 本期 | 对比基准 | 排期 | 特别关注 |
|---|---|---|---|---|
| 日报 | **今日**（22:50 是营业日中段，约 88% 完整） | 昨日 | 每天 | 缺货归因、断码预警 |
| 周报 | **上周一~上周日**（完整 7 天） | 上上周一~上上周日 | 每周一 | 品类趋势、供应商稳定性 |
| 月报 | **上月1号~上月末**（完整月） | 上上月1号~上上月末 | 每月 1 号 | 环比叙事、结构性变化 |

> ⚠️ 2026-10-23 修订：本期口径与排期都改了，原表是错的。
>
> **原表写的是「本周（周一起）vs 上周同期」/「本月 vs 上月」**，
> 且没有排期列。那套口径**只在每天推的时候才成立** ——
> 而周报若每周一推，取「本周一~今天」就只有 1 天，一份只覆盖 1 天的周报
> 没有任何内容；月报每月 1 号推同理。
>
> 现在三者各自的锚点不同，这是**有意的**：
>
> - 日报取**今日**：22:50 是营业日中段，店长要的是「今天怎么样、现在补什么」；
> - 周报/月报取**上一个完整周期**：周一早上看上周、1 号看上月，
>   这才是店长对「周报/月报」的预期。
>
> 这套口径与 Flutter 端文案逐字一致
> （`ai_report_rules.dart`：「每天推送当天汇总」/「每周一推送上周汇总」
> /「每月 1 日推送上月汇总」）。
>
> ⚠️ **月报两期天数可能不同**（2月28天 vs 1月31天）——
> 那是真实口径差异，由 `calendar.Compare` 判 limited 并在卡片上说明，
> 不做静默折算。
>
> ⚠️ 日报是**部分日**（22:50 抓取 ≈ 88% 完整度），环比「完整昨日」时
> 会有约 -12% 的观感。这是「当日实况」语义的固有代价，
> 卡片上的「部分日」标注是后续工作。

### 3.3 自用供应商识别（三层，**不可硬编码**）

实测 `ysx` 源库结论：

| 层 | 规则 | 实测依据 |
|---|---|---|
| 1 | `supcust_flag='C'`（客户不是供应商） | 49 个客户：运营部、中铁五局搅拌站、银海物业… |
| 2 | `sup_type<>'1'`（自用/直供） | 4 个：乐园公司、内蒙古伊利集团、新龙净菜、自产 |
| 3 | **名称关键词命中**（可配置） | `自购蔬菜`、`水果（自营）` 类型是 1 但语义是自营 |

⚠️ **第 3 层必须外置可配置**：每个门店的自用命名不同
（"自购""自营""自产""乐园""内部周转"…）。硬编码 = 换一家门店就漏排。

**销售归属用 `t_rm_daysum.supcust_no`**（实测 100% 非空，每日 70-80 个供应商），
而不是从商品档案反推 —— 流水上的归属才是真实成交的归属。

### 3.4 后台可观测（完整推理审计）

每次推理记录并可在后台查看：

- 事实包全文（可折叠）
- 最终 prompt（**含版本号**）
- LLM 原始输出
- 解析后的结构化结论
- token 用量 / 耗时 / 是否降级 / 降级原因

**目的**：优化 prompt 靠的是对比"同一份事实包在不同 prompt 版本下的输出差异"，
只存最终结论等于放弃这个能力。

## 4. 明确不做（避免范围蔓延）

| 不做 | 理由 |
|---|---|
| 预测式补货建议 | 需要更多历史与算法沉淀，属独立产品 |
| 多门店横向对比排行 | 当前是单店隔离，多店对比是另一个权限与口径问题 |
| LLM 自主多轮查询 | 见 2.2 权衡 |
| 语音播报 | 非核心诉求 |

## 5. 验收标准

1. 日报在配置时间自动送达指定企微群，卡片明确区分日/周/月
2. 缺货商品被正确标注为「缺货」而非「滞销」，且证据可查
3. 自用供应商不出现在供应商排行中，且后台能看到排除原因
4. LLM 失败时规则模式仍能出报告，且标注「规则模式」
5. 后台可查到完整推理上下文（含 prompt 版本）
6. 事实包字符数在阈值内，token 用量可统计
