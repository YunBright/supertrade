# 猪肉毛利核算方案 v4 —— 单次实盘 + 两位置库存 + 移动加权平均

> 目标:**单日毛利**、**部位毛利**、**长期毛利**、**整猪毛利**都可算、且可对账。
> 状态:v4(2026-10-23)。本版按三条新约束重构:
> ① **只有一次实盘**(日终);"售前重量" = 昨日日终重量,沿用不重称;
> ② **两套库存**:猪肉台(当日)/ 全店(= 猪肉台 + 冷库),**没有"只查冷库"**;
> ③ **长期毛利**与单日毛利并列。
>
> 变化速览:v3 → v4
> - ❌ 删掉 **P0 售前盘点**(不再需要任何新增的人工盘点动作)
> - ❌ 删掉 **隔夜损耗的"测量"**(实测不了,不假装能测);差额改名为「隔夜失重/盘亏」并显式展示
> - ✅ 新增 **库存位置维度**(猪肉台 / 冷库)+ 自动过夜搬运
> - ✅ **"酒店统收"泛化**:不再只服务板油,而是冷库里任何未卖完的部位
> - ✅ 新增 **长期毛利**口径
> - ⚠️ 成本法切换(移动加权 vs 旧 LLM 摊销)仍待确认

---

## 0. 一句话

**把猪肉当普通零售存货管:SKU 级移动加权平均成本 + 每天一次日终实盘 + 冷库/猪肉台两位置。**
⇒ 单日毛利变成一道**纯减法**,不依赖 LLM、不依赖"猜昨天的货归哪头猪"。

```
本期毛利 = 本期销售收入 − (期初结存金额 + 本期入库金额 − 期末结存金额)
```

## 1. 现有算法最严重的缺陷(v3 已述,这里作为动机)

### ⚠️ 今天的猪没出过的部位,今天卖的钱成本是 0 ⇒ 毛利率 100%

```go
// gross_margin.go
pigs := 当日进场的猪                        // ← 只有今天的猪!
costForCut[cut] = Σ pig(今天的猪)(pig_cost × 该猪该部位占比)
case purch.IsZero(): ratio = 1             // 今天没产出 ⇒ 比例 100%
consumedCost := costForCut[cut].Mul(ratio) // ← 但 costForCut = 0
```

⇒ 今天卖昨天剩的五花(今天没进猪)⇒ **成本 0,毛利 = 收入,毛利率 100%**。
⇒ **每天都发生**(只要店里在卖隔夜货)。现有算法根本没有"昨天"的概念。

⇒ **v4 的期初(昨日日终重量)直接消灭这个 bug** —— 这是整个重构的起点。

### 其余 4 个缺陷

| # | 缺陷 | 后果 | v4 的修法 |
|---|---|---|---|
| ② | 特价销售整行被丢弃 | 佳乐:金额 ~5%、重量 ~10% 消失 | `promo_skus` + 解析处加分支 |
| ③ | 成本分摊基数只用 LLM advice;`history_avg` 返空 cuts ⇒ 整猪成本摊不出去 | 毛利大幅**高估** | 基数改"实际产出 kg",缺失才用统计基线 |
| ④ | 未被任何部位覆盖的 kg(血、修边、称重误差)成本摊不出去 | 毛利高估 | 显式化:切分损耗 + 隔夜失重/盘亏 |
| ⑤ | 当日实盘按 cut **覆盖**而非累加 | 多 SKU 时实盘/差异全错 | 改累加 |

## 2. 日循环(只有一次实盘)

### 2.1 时间轴

```
开卖前(自动)
  ⑤ 冷库 → 猪肉台:把"昨晚称好的那一袋"搬上台,量 = 昨日日终盘点值
     ⇒ "售前重量" = 昨日日终重量(沿用,不重称)
     ⇒ 无需任何人工录入;仓管若只想上一部分,可在界面上改量

日间
  ⑥ 录今日进猪(头数 / 毛重 / 进价 / 品种 / 供应商)
  ⑦ 分割单品补录(pig_cuts:部位 + 重量)   ← 成本分摊依据 + 分割模型训练数据
  ⑧ POS 销售:零售(部位 SKU)+ 特价(promo SKU)

日终(唯一实盘)
  ① 猪肉台实盘:每个 SKU 剩余 kg              ← 唯一的实盘
  ② 自动:猪肉台 → 冷库(过夜保鲜)
  ③ 录分割副产入冷库(如板油:当日余量)
  ④ 冷库 → 酒店统收(产生收入,几天一次)

日终核算
  ⑨ 移动加权平均 → 单日毛利 / 部位毛利
  ⑩ 特价缺口分摊
  ⑪ 长期毛利(日快照累计)、成本对账行、切分损耗、隔夜失重/盘亏
```

### 2.2 "隔夜损耗"怎么办 —— 诚实处理

用户口径:**昨晚称好的那一袋,今天按昨天的重量上台** ⇒ **隔夜失重无法测量**。

量化影响:
```
期初数量 Q0 = 昨日日终重量(昨晚称的,偏大)
今天实际剩  = 今日实盘(今天称的,已失重)
⇒ 系统推算的"卖出量" = Q0 − 今日实盘,比真实销量**略高**(高估部分 = 隔夜失重)
```
量级:隔夜失重 ≈ 1~3%/天 × 昨日剩余量。对**当日销量**的影响 = 失重 × (昨日剩余/今日销量),
典型 <2%;对**月报销量**的累计影响 ~10~20%(因为每天都高估一点点)。

⇒ **对策(不是测量,是标注 + 归因)**:
1. 差额显式命名为 **「隔夜失重/盘亏(含称重误差)」**,进损耗表,进损益;
2. 报表顶部标注:"期初沿用昨日日终重量,**未做隔夜失重修正**;实测销量可能被高估约 X%";
3. X% 由系统自算(近 7 天 该店/该 SKU 的 平均(昨日日终−今日实盘)/昨日日终)。

⇒ **不假装能测,但让偏差可见、可监控、可逐步收敛**(若将来改成每天重称,偏差自动归零)。

## 3. 库存位置模型(两套库存)

### 3.1 位置定义

| 位置 | wire | 含义 |
|---|---|---|
| 猪肉台 | `counter` | 当日在售、会被顾客看到的货 |
| 冷库 | `cold_store` | 存放:过夜保鲜 / 分割副产(板油) / 待统收 |
| **全店** | `all` | = 猪肉台 + 冷库(**查询枚举,不是真实位置**) |

### 3.2 查询口径(按用户要求)

| 查询 | 语义 |
|---|---|
| **默认** | 猪肉台 `counter` |
| 可选 | 全店 `all`(= counter + cold_store) |
| **不提供** | 只查冷库 |

⇒ API: `GET /stock?branch=&scope=counter|all`(默认 counter)。
`scope` 只有两个取值 —— **不要**暴露 `cold_store`,因为"冷库单独看"没有业务含义。

### 3.3 流转(自动为主)

| 动作 | 触发 | 记什么 |
|---|---|---|
| **生产入库** | 分割产出上猪肉台 | 猪肉台 +kg(同时是移动加权的"本期入库") |
| **生产入冷库** | 分割副产(板油)录入 | 冷库 +kg |
| **日终盘点 → 过夜** | 盘点后自动 | 猪肉台 −kg / 冷库 +kg(金额不变,只是位置变) |
| **开卖前搬上台** | 自动(或仓管改量) | 冷库 −kg / 猪肉台 +kg |
| **日终实盘校正** | 盘点与账面差 | 盘盈/盘亏 → 损耗 |
| **酒店统收** | 冷库出 | 冷库 −kg / 收入 +金额 |

⇒ **转库不改变金额**(成本跟着货走)⇒ 移动加权单价**全店一个**,位置只是"可售性"标记。

### 3.4 数据模型

```
sku_stock_positions(
  branch_id, cube_product_id, location,      -- 'counter' | 'cold_store'
  qty_kg, updated_at
)
PRIMARY KEY (branch_id, cube_product_id, location)

sku_cost_states(                               -- 全店移动加权单价(当日有效)
  branch_id, cube_product_id,
  qty_kg, amount_yuan, moving_avg_unit_cost, last_biz_date
)
PRIMARY KEY (branch_id, cube_product_id)

sku_cost_daily(                               -- 日快照:可审计、可回看、可算长期毛利
  branch_id, biz_date, cube_product_id,
  opening_qty, opening_amount,
  produced_qty, produced_amount,
  sold_qty, sold_amount,
  bulk_sold_qty, bulk_sold_amount,
  waste_qty, waste_amount,
  closing_qty, closing_amount,
  moving_avg_unit_cost,
  counter_qty, cold_store_qty,                -- 期末两位置分布
  data_source                                  -- actual | partial | estimated
)
```

## 4. 成本核算主口径:移动加权平均(per SKU,全店)

### 4.1 公式

```
期初数量 Q0 = 昨日日终盘点剩余(全店)                ← 自动,零人工
期初金额 V0 = Q0 × 昨日该 SKU 的移动加权单价

本期入库数量 Q1 = 今日分割产出到该 SKU 的 kg
本期入库金额 V1 = Σ(今日产出该 SKU 的每头猪的成本分摊额)

可售总金额 = V0 + V1        可售总数量 = Q0 + Q1
本期移动加权单价 = 可售总金额 / 可售总数量

期末数量 Q2 = 今日日终实盘(全店)
期末金额 V2 = Q2 × 本期移动加权单价

本期销售成本   = 可售总金额 − V2
本期销售毛利   = 本期销售收入 − 本期销售成本
```

### 4.2 "本期入库金额 V1"—— 唯一还需要摊猪成本的地方

```
对每头今日进场的猪 P:
  P 总成本 = 进价 × 毛重(或直接录采购金额)
  P 分割出的各 SKU kg = 单品补录;缺失 → 统计基线(§7)预估
  P 的各 SKU 成本分摊 = P 总成本 × (该 SKU kg / P 的产出 kg 合计)
```
⇒ 分母用 **P 的实际产出合计**(不是 `gross_weight`)
⇒ **差额自动就是「切分损耗」**(§6.2)。

### 4.3 为什么这个口径明显更准

| 维度 | 现有(LLM 摊销) | v4(移动加权平均) |
|---|---|---|
| 卖昨天的货 | 用**今天**的猪的成本;今天没进猪 ⇒ 成本 **0** ⇒ 毛利 100% | 期初按昨日移动加权单价入账 ⇒ 成本真实 |
| 多日累积库存 | 无概念 | 移动加权天然处理 |
| 冷库里的旧货 | 无概念 | 位置可追踪,统收时按全店加权成本结转 |
| 隔夜失重 | 无记录 | 显式为「隔夜失重/盘亏」 |
| 切分损耗 | 无记录 | 显式化 |
| 可对账 | ❌ | ✅ 对账行(§6.3) |

## 5. 特价 SKU:长期配置 + 日终缺口分摊

### 5.1 配置(长期,像部位映射一样 —— 用户已确认)

```
promo_skus(
  id, branch_id, cube_product_id, product_name,
  note, active, created_at, updated_at
)
UNIQUE(branch_id, cube_product_id)
```

### 5.2 销售行不再被丢弃

`sale.completed` 本来就带 `sku_id / qty / amount` —— 只是被"查不到映射就丢行"丢掉了。
⇒ **在解析处加一个分支**:
```
若 sku_id 命中 promo_skus:
    落 line_sales_by_pigs(cut_type="promo", source="pos_promo")
    金额与 kg 都进来;部位归属留待日终分摊
```

### 5.3 日终缺口分摊(有了期初 ⇒ 从"推断"变成"可对账的差值")

```
对每个部位 c:
    gap_c = 期初_c + 入库_c − 正常销量_c − 日终剩余_c − 已记报损_c − 隔夜失重_c
```
- `gap_c > 0` ⇒ 该部位"账面少了 kg" ⇒ 被特价处理;
- 特价总量 `K = Σ 特价销售行.kg`(实测)、`R = Σ 特价销售行.amount`(实测);
- 权重 = 缺口为主(α=0.7)+ 滞销度(周转天数)为辅(见 v2 §3.2);
- `promo_kg_c = K × w_c`、`promo_amount_c = R × w_c`;
- 残差进「未分摊残差」行,显式列出。

> **分摊的重要性下降了**:移动加权把成本与收入绑在同一个 SKU 上 ⇒ 分摊错了只影响
> "特价收入记到哪个部位",成本跟着该部位的移动加权单价走,自动一致。

## 6. 显式化的"消失的 kg"(以前全被吃掉)

### 6.1 隔夜失重/盘亏
`昨日日终 − 今日实盘`(逐 SKU)⇒ 自动。**不可单独测出真隔夜失重**(含称重误差),故命名带"/盘亏"。

### 6.2 切分损耗
`今日进猪毛重 − 今日产出 SKU kg 合计 − 今日副产入冷库 kg` ⇒ 自动。
(修边掉料、滴水、血水 —— 以前**完全不在任何表里**,成本凭空消失。)

### 6.3 成本对账行(报表底部)
```
Σ 各 SKU 本期销售成本 == Σ 当日进猪采购成本 + 期初存货成本 − 期末存货成本
误差必须为 0(有损耗/盘亏项时误差 = 已显式化的损耗额)
```
⇒ **整猪毛利准不准,一眼可判**。

## 7. 分割重量预测:数据能积累,但**建议别用 LLM 做数值回归**

### 7.1 数据已经在攒
- `whole_pigs`:体重、品种、供应商、进价、日期
- `pig_cuts`:**每头猪实际分割出的各部位 kg** ← 标签
⇒ 一头猪 = 一个样本。**前提是单品补录的录入率上来。**

### 7.2 ⚠️ LLM 不适合这个任务
"300kg 的猪能出多少五花"是**数值回归**。LLM 给的是语言先验,不是从样本拟合;
而品种/膘情/季节/师傅手法是**结构化特征**,该用统计/回归。

| 阶段 | 预测器 | 说明 |
|---|---|---|
| **短期(马上)** | **分层统计基线**:`体重段 × 品种` → 各部位均值 + 分位数 | 不需要模型,`pig_cuts` 一有就能算;比现在的 LLM 准 |
| **中期** | 回归模型(梯度提升) | 样本够了再上;仍比 LLM 便宜一个数量级 |
| **LLM 新定位** | **兜底 + 解释层** | 冷启动情况 + "这头猪分割异常"的文字说明 |

### 7.3 样本量现实感
1 头/天 ⇒ 1 年 ≈ 365 头 ⇒ `体重段(10) × 品种(3)` 每格约 12 头 ⇒ 勉强可用。
更细建模需要**多店数据汇聚**。
⇒ **推动单品补录录入率,本身就是最有价值的投资**:它同时是成本分摊依据、
分割模型训练数据、特价分摊精度来源。

## 8. 长期毛利

### 8.1 口径
```
期间(周/月/季/自定义)毛利 = 期间总销售收入 − 期间总销售成本
  收入 = 期间 POS 零售 + 期间特价 + 期间酒店统收
  成本 = 期间各 SKU 的移动加权销售成本累计(日快照汇总)
```
- **期初存货的成本在售出时按移动加权结转** ⇒ 自然进入期间成本 ⇒ 口径正确;
- 可按 **SKU / 部位 / 门店 / 期间** 聚合与对比。

### 8.2 为什么长期毛利比单日毛利更"终局正确"
单日毛利会被**库存波动**扭曲:今天卖得多不等于毛利高(可能卖的是便宜的陈货),
今天毛利低也可能是好货囤着没卖。
⇒ **单日毛利用于"当期经营诊断";长期毛利用于"真实盈利能力"** —— 两者都要,并列呈现。

⇒ 这也意味着:刚切换成本法时,**单日毛利会剧烈波动**(期初成本口径变了),
必须用长期序列来看趋势,别用切换前后的单日数字直接比较。

### 8.3 接口
```
GET /gross-margin?branch=&date=                 -- 单日(现状扩展)
GET /gross-margin/period?branch=&from=&to=&group_by=cut|sku|day  -- 长期
```

## 9. 酒店统收(原"板油台账"泛化)

用户新描述:冷库里的货,**除了重新上猪肉台,还有酒店收购**。
⇒ **板块油只是其中一种**,不必单开台账 —— **统一成"冷库 → 统收"通道**。

```
bulk_settlements(
  id, branch_id, from_date, to_date,
  qty_kg, unit_price_yuan, amount_yuan,
  counterparty, settled_at, operator_id, note
)
bulk_settlement_allocations(                    -- FIFO 分配到具体产出/批次
  id, settlement_id, source_type, source_id,   -- 'production' | 'stock'
  cube_product_id, cut_type, pig_id, qty_kg, amount_yuan, production_date
)
```
结算回写:
```
line_sales_by_pigs(
  branch_id, sale_date = production_date,     -- ★ 记在产出日
  pig_id, cut_type, qty_kg, amount_yuan, unit_price_yuan,
  source = "bulk", pos_line_id = "BULK-<settlement_id>-<ref>"
)
```
⇒ 现有毛利引擎直接就能算,不用改毛利算法。

> ⚠️ **统收的货来自冷库**,其成本应按**该 SKU 的移动加权单价**结转(全店口径),
> 而非按某头猪的成本 ⇒ 与"逐猪归因口径"会有差,报表要分开标注(见 §10.3)。

## 10. 取舍与隐患

### 10.1 必须接受的三条
| # | 取舍 | 说明 |
|---|---|---|
| T1 | **成本法切换** | 移动加权 vs 旧 LLM 摊销**口径不同、历史不可比**。需定"切换日",之前标注旧口径。 |
| T2 | **隔夜失重不可测** | 期初沿用昨日重量 ⇒ 销量略高估。**不假装能测**,但差额显式化 + 给出自估偏差百分比。 |
| T3 | **两套成本口径并存** | 移动加权(SKU/部位/店,权威零售口径)+ 逐猪归因(整猪,管理口径)。两者有差,这个差本身是指标(混合/损耗/盘亏),但报表必须**分别标注、不能混**。 |

### 10.2 已消除的成本(相对 v3)
- ❌ 售前盘点(新增日常动作)—— **不需要了**,期初自动取昨日日终值;
- ❌ 手工"搬上台"录入 —— 默认自动全搬,需要时才改量。

### 10.3 其它隐患(沿用 v2/v3,此处不重复)
- 缺口 ≠ 特价 ⇒ **总量用实测,缺口只定比例**;
- LLM 高估会让真凶的缺口变负 ⇒ `应产出`优先用实际值;
- 分摊结果**不落回**销售表(避免自反馈);
- 硬依赖日终实盘 ⇒ 缺盘点时降级输出"未盘点"标记。

### 10.4 两个"白送"红利(建议一起做)
1. **二次分摊到单猪**:店级分摊后按"该部位各猪入库 kg"再分 ⇒ 单猪也拿得到特价收入(**否则"整猪毛利"其实还是店级**)。
2. **分割重量统计基线**先上:不依赖 LLM,`pig_cuts` 一有就能算,立刻提升成本分摊与特价分摊精度。

## 附录 A:UI 设计(猪肉台 / 冷库)

### A.1 关键结论:**盘点盘的是"猪肉台",不是"全店"**

按门店实际流程反推位置流水:

```
开卖前   搬上台 T(仓管定,可部分/可不上)   冷库 −T ; 柜台 +T     ← 全店不变
日间     分割上架                          柜台 +产出
         零售销售                          柜台 −销量
         分割副产(板油)入冷库             冷库 +kg
日终     盘点 P = 柜台实盘
         ⇒ 全店实盘 = P + 冷库余额(此刻)
         ⇒ 记入 sku_cost_daily.closing_qty
         ⇒ 过夜:冷库 +P ; 柜台 = 0                              ← 全店不变
```

⇒ **全店 = 柜台 + 冷库,恒等**;全店日终余额 = 柜台实盘 + 冷库余额;
⇒ 次日全店期初 = 上日 `sku_cost_daily.closing_qty`。
⇒ **仓管的盘点工作量完全不变**(还是盘柜台),**不需要拆成"柜台/冷库"两段录入**。

### A.2 三个界面角色

| 界面 | 性质 | 内容 |
|---|---|---|
| **① 开市准备 · 搬上台**(新) | 每日一次 | 列出冷库里的 SKU(按部位分组),每行填"搬多少 kg 上猪肉台";留空 = 不上。快捷:「全上」/「按昨日搬台量」建议值。**不称重**(按昨晚的重量搬) |
| **② 日终盘点**(轻改) | 每日一次 | 仍然 per-SKU 实盘、**仍然只盘猪肉台**。改动见 A.3 |
| **③ 库存查询**(新) | 随时 | **默认猪肉台**,可切 **全店**;**不提供**"只查冷库"。每行:SKU / 部位 / 数量 / 移动加权单价 / 冷库余额 / 压货天数 |

### A.3 盘点页的具体改动

1. 顶部口径说明:"本次为**猪肉台**实盘;全店余额 = 猪肉台 + 冷库(系统自动)";
2. 每行加**参考列**:`上次结存` / `账面猪肉台` / `冷库余额`,差异高亮 ⇒ 仓管可核对;
3. **改成"全量列出应盘 SKU"**,而不是"从下拉里挑一个加一个":
   - 默认只列**昨日有结存 或 今日有产出**的 SKU(动态应盘清单),加"显示全部"开关;
   - ⚠️ **既有隐患**:`is_complete=true` 的语义是"全店都盘了",而当前后端
     `snapshotFromCalc` 会把**没录入的部位/ SKU 填成 actual=0**
     ⇒ **漏录 = 盘空**。改成全量列出 + 显式填数(可填 0)后,这个隐患才消除;
4. 提交后自动执行"过夜搬运"(柜台 → 冷库)。

### A.4 为什么不把盘点拆成"柜台段 + 冷库段"
- 那样仓管要**开冷库、逐 SKU 填两次** ⇒ 工作量翻倍;
- 而**冷库余额的精度要求低** —— 它只影响"可售量查询"与"压货天数",**不影响毛利**
  (毛利用的是全店口径,而全店 = 柜台实盘 + 系统冷库余额);
- ⇒ 拆两段是**用一倍工作量换一个不影响钱的数字**。

### A.5 压货天数与失重偏差
冷库可长期压货 ⇒ 货的重量沿用入库时的数字,失重逐日累积 ⇒
- 报表给 **冷库平均压货天数**(冷库批次的入库日加权);
- 失重偏差自估:近 7 天 `(昨日全店 − 今日全店实盘) / 昨日全店`,报表标注"实测销量可能被高估约 X%";
- 冷库压货超过阈值(如 7 天)⇒ **告警**(该走特价或统收了),这直接支撑特价分摊与统收决策。

### A.6 盘点归属:猪肉归鲜肉域,通用盘点排除(不做第三套)

**现状:已经两套盘点,而且猪肉会被盘两次。**

| | 通用盘点(`supertrade-stocktake`) | 鲜肉盘点(`supertrade-fresh-meat`) |
|---|---|---|
| 类型 | `general` / `produce` / `plan` / `recheck` —— **没有 meat** | `pork_cuts_stocktakes` |
| 盘什么 | SKU 级,算 `stock_levels` 账实差异 | 部位/SKU 级,算毛利、出成率 |
| 范围怎么定 | **人工预选计划清单** | 部位映射表 |

`AddPlanItems` / `AddLine` **没有任何按类目排除的机制**(传什么加什么)⇒
**`general` 盘点会把猪肉 SKU 一起盘进去** ⇒ 同一批猪肉两个班组盘两次、两个数字、两套口径,
两边都不算错,但没人知道该信哪个。

⇒ **决策:不做第三套。**
1. **通用盘点侧**:`AddPlanItems` / `AddLine` 落库前判断商品是否属猪肉类目
   (cube `product.category_id`:佳乐 `1201` / 富百家 `010303`)⇒ 是则**拒绝**并提示
   "猪肉请用鲜肉盘点"。**服务端拒绝,不靠前端过滤**(前端会被绕开,
   绕开的后果是"两个数字打架"且无人发现)。
2. **鲜肉域**:现有鲜肉盘点**升级成"猪肉盘点管理"模块**(不是新服务)——
   它本来就订阅 `sale.completed`、已有部位映射、已在算鲜肉毛利、已有独立表与端点。
   4 个子界面:开市准备 / 日终盘点 / 库存 / 毛利与出成。

**为什么不是新服务**:猪肉盘点的产出不是库存差异而是**毛利与出成率**
(按部位 + 按猪 + 按天),与通用盘点(SKU 级账实差)算法/维度/周期都不同;
新服务要重做鉴权、事件、清理、前端路由,而 fresh-meat 已有 ⇒ 边际收益≈0、
跨服务一致性成本很高(又一次"两套口径")。
