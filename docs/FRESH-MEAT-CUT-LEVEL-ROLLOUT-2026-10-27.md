# 鲜肉毛利改「部位级」—— 上线说明与门店指引

> 日期：2026-10-27
> 施工图：`FRESH-MEAT-CUT-LEVEL-COST-CHAIN-2026-10-27.md`（口径决议 R1~R6）
> 影响面：`fresh-meat` 服务（成本链）+ Flutter 毛利表/盘点页 + 契约守卫

---

## 1. 一句话

**以前"猪蹄"这一行是把猪脚、猪手两个货号的账各自算完再拼起来的，所以会出现"进货 4.7、销售 16.9、应有却还是正数 5.0"这种自相矛盾；现在库存、成本、毛利一律按部位算，货号只负责"卖了多少、卖了多少钱"。**

---

## 2. 改了什么

| 层 | 改动 |
|---|---|
| 表 | 新增 `cut_cost_daily`（部位级成本日快照）/ `cut_cost_states`（部位级成本状态）；旧 `sku_cost_daily` / `sku_cost_states` **停写、保留只读** |
| 引擎 | `computeSkuDailyCosts`（SKU 级）→ `computeCutDailyCosts`（部位级）；期初/期末/成本/毛利全部按部位 |
| 恒等式 | `期初 + 入库 − 销售 − 统收 − 报损 = 应有` **逐部位闭合**；对账差额恒 0 |
| 负数 | 「应有」**不再裁 0** ⇒ 负数 = **账面短卖**（卖超了库存），必须看得见 |
| 毛利表 | 部位行 = 成本口径；货号子行只显示**销售 kg / 营收**；负数应有红字标注「账面短卖」 |
| 盘点页 | 应盘集合改**部位口径**（部位有期初或产出 ⇒ 该部位下所有货号都要盘），杜绝漏盘 |

**为什么以前会算错**：期初结转是按**部位**录的，旧引擎却把它 100% 记到该部位"主货号"（猪脚 01411）上，另一个货号（猪手 01412）账面恒为 0 ⇒ 猪手卖出 7.97kg **成本算成 0** ⇒ 毛利率 100%。

## 3. 门店会看到什么变化（2026-10-02 店 00 猪蹄）

| 项目 | 改前（旧 SKU 级） | 改后（部位级） |
|---|---|---|
| 期初 | 9.23 kg / 73.84 元 | 9.23 kg / 73.84 元（不变） |
| 进货 | 4.73 kg | 4.73 kg |
| 销售 | 16.8957 kg / 347.10 元 | 16.8957 kg / 347.10 元（不变） |
| **应有** | **+5.04 kg（自相矛盾）** | **−2.94 kg（账面短卖 2.94 kg）** |
| 销售成本 | 103.63 元 | 196.21 元 |
| 毛利 | 243.47 元（70.1%） | 150.89 元（**43.5%**） |

- 全店 2026-10-02：毛利从 **1283.15 元** 下降（降幅来自**此前没入账的成本**：12 个部位账面短卖 41.4 kg ≈ 733 元，另有 5 个货号零成本销售占全店营收 12.4%）。
- ⚠️ **这是"变准"，不是"亏了"**：以前这些销售没计成本，毛利是虚高的。

## 4. 门店要做的唯一一件事：补「期初结转」

**入口**：App「鲜肉 → 设置 → 期初结转」
**接口**：`PUT /stock/openings`

```json
{"openings": [
  {"cut_type": "trotter", "cold_store_kg": "9.23", "unit_price_yuan": "8", "biz_date": "2026-10-01"}
]}
```

规则：

1. **按部位录**（不是按货号）：猪蹄 = `trotter`，五花肉 = `belly`，肋排 = `rib`……
2. **必须有单价**（`unit_price_yuan > 0`）：期初是**已经付过钱的货**，单价 0 ⇒ 那批货零成本 ⇒ 毛利虚高（服务端会拒收单价 0）。
3. **生效日** = 这批货所属的那一天（现在线上已有猪蹄 2026-10-01 这一行，**其它部位照这个日子录**，不要改它）。
4. **先盘冷库再录**：把 2026-10-01 早上冷库里各部位的重量和当时的进价填进去。

> ⚠️ 改造前补录只能改善部位层的"应有"（旧引擎仍会摊到主货号）；**改造上线后补录才真正生效**。
> ⚠️ 补录**不要在真实门店反复试**：录完会重推整条余额链，历史日的毛利会跟着变（这是特性，不是 bug）；审计冻结后不能改。

## 5. 上线步骤

1. 部署 `fresh-meat`（P1 引擎 + P2 周边**一起上线**，避免"部位口径 per_cut + 旧口径 per_sku"的中间态）。
2. 生产只读核对（不打写操作）：
   - `POST /api/v1/login/auth/login/password` 取 token；
   - `GET /api/v1/fresh-meat/gross-margin?date=2026-10-02` + `X-Branch-ID: 00`；
   - 核对：**期初存货成本仍是 73.84**、猪蹄**应有 = −2.94**、**对账差额 = 0**。
3. 契约守卫（deployer，只读 GET，生产 00/01 店）必须全绿：
   - `PerSku_HasNoStockKeys`（货号行不再带库存/成本键）
   - `PerCut_IsTheOnlyStockScope`（部位行 `expected_remain_kg` 存在且可为负、`diff_yuan == 0`）
   - `CutLevel_IdentityCloses`（逐部位恒等式闭合）
   - `CutLevel_SoldMustHaveCost`（卖了货的部位成本不得为 0）
4. Flutter 发版（毛利表 + 盘点页部位口径）。
5. 通知门店：毛利数字会下降（原因见 §3），并请他们补期初结转（§4）。

### 5.1 长期毛利（`/gross-margin/period`）的口径与数据源

> ⚠️ **长期毛利不能只读成本日快照** —— 快照的物化点是"日终盘点 / 审计结转"，
> 而真实门店**从 9 月至今没有盘点单** ⇒ 快照表是空的
> ⇒ 只读快照 ⇒ `group_by=day|cut` 返回**全 0**、`group_by=sku` 成本恒 0
> ⇒ **接口看起来"正常"但没有数据**（2026-10-27 生产实测）。

⇒ 现在改成：**逐日取数，缺口实时算**。

| 那天有成本日快照吗 | 数据来源 | 说明 |
|---|---|---|
| 有（已审计结转的区间） | `cut_cost_daily` | 快，且是**冻结**后的权威值 |
| 没有 | 实时调部位级引擎 | 与每日毛利**同一个引擎** ⇒ 数字一致（正确，但逐日算 ⇒ 月报约 15s） |

⇒ 不变量（已用单测锁住）：**长期毛利 = 每日毛利之和**。

> ⚠️ **审计结转是"逐日物化"的现成机制**：审计第 ③ 步对区间内每一天落成本日快照
> （审计的前置条件 = 区间内每天都有完整日终盘点 ⇒ 审计过的区间每一天都有快照）
> ⇒ 门店开始做日终盘点 + 定期审计结转后，长期毛利会自动变快。

## 7. 长期毛利口径（2026-10-27 第二轮修订）

### 7.1 一句话

**长期毛利与每日毛利现在走同一条链**：今天的期初 = 昨天的期末（链式接续），
⇒ 不再依赖「日终盘点才落快照」⇒ 门店不盘点也能拿到**正确**的长期毛利。

### 7.2 数字会怎么变（提前告诉店长）

| 场景 | 改前 | 改后 |
|---|---|---|
| 毛利水平 | 虚高（9 月显示 100%、10-03 起 97%） | 变低但**是真的**（成本进账了） |
| 对账差额 | 偶发非 0 | 恒 0 |
| 成本算不出来的那几天 | 静默按 0 处理 | **显式标注**（黄字提示 + 说明） |

> ⚠️ 10-02 实测：销售成本 3072.17 → **3253.37**，毛利 408.13 → **226.93**（11.73% → 6.52%）。
> 变低是因为 10-01 卖超的 5.82kg 现在**计入了成本**（以前那部分白送）。

### 7.3 「成本算不出来」是什么意思

某部位**既没有期初库存、当天也没有进货**，又没有任何可用单价 ⇒ 那部分货的**成本算不出来**
（不是成本为 0）⇒ 那几天的毛利被**高估**。

门店侧要做的事只有一个：**在「鲜肉-设置」补期初结转**（按部位录冷库余额 + 进价）。
补上之后，那几天的成本才立得住。

### 7.4 物化点（用户决议：只靠审计结转）

- 日常不新增定时任务。
- **审计结转**逐日物化整条链（审计的前置条件 = 区间内每天都有完整日终盘点 ⇒ 每天都会落）
  ⇒ 门店开始做日终盘点 + 定期审计结转后，长期毛利会自动变快。
- 另外，写路径（录猪 / 大宗 / 搬上台 / 期初结转）之后会**后台**把链重算一遍
  （这是为了「补录往日」也能向下传播，不是另一个物化点）。

### 7.5 回滚

同 §6：`git revert` 后重新部署 `fresh-meat`。⚠️ 已审计冻结的门店，其后数据被冻结 ⇒ 回滚前确认。

## 8. 已知项：长期毛利 / 每日毛利的查询耗时（2026-10-27 生产实测）

### 8.1 现象

| 接口 | 目标日期 | 耗时 |
|---|---|---|
| `GET /gross-margin` | 10-02 | ~0.7s |
| `GET /gross-margin` | 10-12 | ~4.0s |
| `GET /gross-margin` | 10-27 | **~8.9s** |
| `GET /gross-margin/period` | 10-02 ~ 10-27(26 天) | ~8.8s |

⇒ **耗时随"目标日期离基线多远"线性增长**。

### 8.2 根因

`loadCutOpening` 的第 ② 步(上一营业日的实时余额链 `closingForDay`)在**未审计**的门店
会走 `deriveColdChain` ⇒ **每次调用都把整条链重算一遍**。
而链式回溯**每天**都会调一次 ⇒ O(天²)。

⇒ 物化(`cut_cost_daily`)虽然已把成本链接上，但**物理库存链**(`cut_stock_daily`)
仍要走实时推链 ⇒ 加速不明显。

### 8.3 方案(下一轮做)

1. `loadCutOpening` 的 ② 改为**惰性求值 + 请求级缓存**:
   `deriveColdChain` 一次调用就能给出**所有天**的日终结余
   ⇒ 链回溯时每天从它里面取 ⇒ 全链只算一次 ⇒ O(天²) → O(天)。
2. ⚠️ **不能**直接用成本链的结余替代物理库存链的结余 ——
   两者语义不同(账面结余 vs 冷库/柜台实盘结余),且审计后 `cut_stock_daily` 是**冻结**的。
   ⇒ 只能缓存、不能替换。
3. 审计结转之后(`cut_stock_daily` 落地)⇒ ② 直接读快照 ⇒ 本问题自动消失。

### 8.4 当前可接受的结论

- 数字**是对的**(对账差额恒 0、恒等式闭合、链逐日接续)。
- 慢**只影响查询耗时**,不影响数据正确性。
- 门店开始做日终盘点 + 审计结转后 ⇒ 这个问题自然消失(② 读冻结快照)。

## 9. 第三轮修订：报告级 `cost_incomplete` + 区间级提示不再漏报（2026-10-27）

### 9.1 起因（一个真实漏报）

Flutter 标注交付后自审发现：**区间级提示会被漏报**，而且生产场景正好落进缝里。

后端 `PeriodMarginReport` 有**两个**口径，含义差一半：

| 字段 | 口径 | 宽/严 |
|---|---|---|
| `cost_incomplete` | 区间里**有任何一天/部位**算不出来就算 true | **宽** |
| `days_without_cost_baseline` | 只数"**整天所有部位**都算不出来"的天 | **严** |

前端区间级提示原本由 `days_without_cost_baseline > 0` 驱动 ⇒ 生产真实场景漏报：

- 店 00 的 10-01：有 **22 个部位**成本算不出来，但当天**只有部分部位**算不出来
  （trotter 9.23kg@8元 有价）⇒ 那天**不是**"整天缺基线"。
- ⇒ `days_without_cost_baseline = 0` ⇒ **一条提示都不显示**。
- ⇒ 店长只看得到"毛利 13.47%"，完全不知道 10-01 的成本是被低估的。

### 9.2 后端改动

| 改动 | 原因 |
|---|---|
| `PeriodMarginReport` 新增 `cost_incomplete_note` | 与每日毛利 `cost_incomplete_note` 对齐 ⇒ 前端**原样显示后端口径**，不自己拼 |
| `note` 里「其中 N 天成本算不出来」拆成两种分支 | 旧写法在 `cost_incomplete=true` 但 `days_without_cost_baseline=0` 时会拼出**「其中 0 天成本算不出来」** ⇒ 自相矛盾且误导店长（生产实测已复现） |

新文案：

- 整天缺基线（`days_without_cost_baseline > 0`）：
  「⚠ 本区间有 N 天的成本**完全算不出来**（既没有期初结转、也没有进货）⇒ 这 N 天的毛利被高估」
- 部分天 / 部分部位：
  「⚠ 本区间有部分天、部分部位的成本**算不出来**（既没有期初结转、也没有进货）⇒ 那部分成本被低估、毛利被高估」

### 9.3 前端改动

| 文件 | 改动 |
|---|---|
| `lib/domain/fresh_meat/fresh_meat_period_margin.dart` | 解析报告级 `cost_incomplete` / `cost_incomplete_note`（缺字段 ⇒ false / ''，**绝不**「缺了就当有问题」） |
| `lib/ui/fresh_meat/margin/period_margin_cost_warning.dart` | `PeriodMarginDaysWarning` → `PeriodMarginCostWarning`：按**报告**驱动，优先后端原话，缺字段走降级文案 |
| `lib/ui/fresh_meat/margin/period_margin_table.dart` | 触发条件 = `costIncomplete \|\| daysWithoutCostBaseline > 0` |

⚠️ **兼容旧后端**：两个条件都是后端**明确报的事实** ⇒ 缺字段时两者皆空 ⇒ 不显示（不误报）；
旧后端只发 `days_without_cost_baseline` 时也照样能提示 ⇒ Flutter 与后端**可分头发版**。

### 9.4 测试

- **后端**：`TestPeriodMargin_PartialCostIncomplete_ReportLevelFlag`（新增）——
  造「belly 有基线 + trotter 无基线」场景，断言报告级 flag=true、天数=0、两处文案都**不出现「0 天」**。
  ⚠️ 判别力自检：把 `note` 改回旧写法 ⇒ 用例立刻变红（症状与生产事故一致）。
- **前端**：domain 解析 5 条 + 表格 widget 3 条 + 页面 widget 2 条。

### 9.5 契约变化

```json
{
  "cost_incomplete": true,
  "cost_incomplete_note": "⚠ 本区间有部分天、部分部位的成本**算不出来**（既没有期初结转、也没有进货）⇒ 那部分成本被低估、毛利被高估",
  "days_without_cost_baseline": 0
}
```

⚠️ `cost_incomplete` / `cost_incomplete_note` 都是 `omitempty` ⇒ 后端没报时**字段不存在**
⇒ 前端按"没有标注"处理（宁可漏报也不能误报）。
