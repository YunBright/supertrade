## 0. 生产事实（店 00，2026-10-30 实测，**设计的依据**）

| 营业日 | Σ进货 | Σ销售 | Σ期初 | Σ期末 | Σ账面应有 | 数据口径 |
|---|---|---|---|---|---|---|

| 10-29 | 181.709 | 178.149 | 10.000 | 20.879 | 13.560 | `actual`（有完整盘点） |
| 10-30 | 0 | 83.391 | 20.879 | **−62.512** | −62.512 | `estimated`（无盘点） |

- 2 头猪：100.2kg + 98.0kg = **198.2kg 毛重**（`data_source=llm` ⇒ 分割建议来自 LLM 通用先验）。
- 10-29 搬台：1 条 **0.1kg**。
- 10-29 完整盘点（32 行，含重复部位）：`belly`=0、`fat`=0、`bone_shank`=0、`lean`=3.1、
  `leg_front`=4.5、`leg_rear`=11.25(cold 9.9)、`bone_scapula`=1，其余 0。

### 关键结论

1. **10-29 的"短卖"是分摊口径问题，不是总量短缺**：
   总量够（进货 181.709 + 期初 10 = 191.709 ≥ 卖出 178.149），
   但**分部位**上 8 个部位是负的（fat −3.311 / bone_shank −2.789 / shoulder_blade −0.994 …）。
   ⇒ 这是 **AI/基线的建议分割与门店实际卖的不匹配** ⇒ **不该传递到下一天**。
2. **10-30 才是真短卖**：账面只剩 20.879kg，却卖出 83.391kg ⇒ 缺口 **62.512kg**
   （物理上这批肉确实存在 ⇒ 说明**账面记错了**，根因是 LLM 的建议分割偏低 ⇒ 正是 A 方案要修的）。
3. **期初出现负数的直接原因（bug）**：`computeCutDailyCosts` 里

   ```go
   closeK := expectedCloseKg          // 负数（账面短卖）
   if hasStocktake {
       if v, ok := closeKg[c]; ok {   // ← 只有"链的余额 map 里有这个部位"才覆盖
           closeK = v
       }
   }
   ```

   而 `closeKg` 来自 `closingForDay` → `deriveColdChain` → `dailyBalanceTerms.add()`
   **只记正数重量**（`!kg.IsPositive()` 就跳过）⇒ **盘到 0 kg 的部位根本不在余额 map 里**
   ⇒ 盘点单明明写了 0（售罄），引擎却用了**负的账面推演**当期末量
   ⇒ 负数写进 `cut_cost_daily.closing_kg` ⇒ 链把它当**下一天的期初**
   ⇒ **门店看到"期初有负数"**。

## 1. 短卖口径（#5）

### 1.1 三个概念必须分开

| 名称 | 含义 | 处置 |
|---|---|---|
| **建议分割 S_c** | AI / 统计基线算出来的**建议** | 照旧（不是实际） |
| **实际分割 A_c** | 当日该部位**真实分割产出** | 由全店恒等式解出；**分部位的负数只是分摊口径** |
| **短卖** | **当日总量**上"卖出 > 账面能支撑"的缺口 | **只有总量口径才算短卖** |

### 1.2 规则

- **R1 期末量不为负**：有完整盘点单时，**盘到的部位（含 0 kg）** ⇒ 期末量 = 实盘（≥0）；
  没有盘点单时，期末量 = `max(账面推演, 0)`。
  ⇒ **链上永远是 ≥0 ⇒ 下一天的期初不会有负数**。
- **R2 分部位的账面不足只作提示**：`cut_short_sell_kg = max(0, 卖出+统收+报损 + 期末 − 可售量)`，
  **不传递、不进链**（它是建议分割与门店实际卖的不匹配）。
- **R3 当日总量短卖才算数**：
  `short_sell_kg = max(0, Σ(期初+进货) − Σ(卖出+统收+报损) − Σ期末)`。
  - 10-29：`191.709 − 178.149 − 20.879 = −7.319` ⇒ **0**（其实是盘盈 7.3kg）。
  - 10-30：`20.879 − 83.391 − 0 = −62.512` ⇒ **62.512**（真短卖）。
- **R4 真短卖才传递**：链上状态带 `shortSellKg`（结转过来的）⇒ 次日显示「累计短卖」；
  **只做传递与标记，不回到负库存**（期初仍然 ≥0）。
- **R5 短卖必须计成本**：短卖的那部分货**按当期可用单价计成本**
  （链上传下来的上期移动加权单价 → 兜底价）⇒ **不许成本算不出来 ⇒ 不许毛利虚高**。
  ⇒ 10-30 那 14 个 `sales_cost_yuan=0` 的行会变成真实成本 ⇒ **毛利数字会变小**（预期）。
- **R6 描红 + 阻断审批**：任何一日 `short_sell_kg > 0` ⇒
  ① 报表里**描红**；② `POST /stock/audit`（审计结转）**拒绝**；
  ③ `GET /stock/audit/precheck` 列出这些天。

### 1.3 对账恒等式（不能破）

现在的恒等式：`期初 + 入库 − 销售 − 统收 − 报损 − 期末 = 差额(应=0)`。
加了「短卖」这一项后必须是：

```
期初 + 入库 + 短卖(补) − 销售 − 统收 − 报损 − 期末 = 差额(应=0)
```

⇒ 对账行新增 `short_sell_kg` / `short_sell_yuan` 两个分量 ⇒ **差额仍恒等于 0**。

### 1.4 「实际分割公式」要不要重写？

**不重写**。理由：A_c 的定义（`全店期末结余 + 销售 + 统收 + 报损 − 全店期初`）
是**物理恒等式**，它在**总量**上永远成立（分部位才有分配误差）。
owner 说的「该公式不应该出现短卖」在**总量**口径上是对的 ⇒
**R1~R3 就是把"分部位误差"与"总量短缺"分开的实现**。
⇒ 公式不动，动的是**怎么用 A_c**（期末量取实盘 / 不裁负进链 / 总量口径判短卖）。

## 2. 基线模块（#1 / #2 / #3）

### 2.1 选池口径不变

```
recN ≥ MinForecastSamples(5) ⇒ 用实录池（sample_source=recorded）
否则 estN ≥ 5               ⇒ 用估计池（sample_source=estimated）
否则                        ⇒ 取样本多的那个留痕，但**不可用**（回退 LLM）
```

### 2.2 新增：`manual_generated`（owner 第 3 点补充）

管理员按「某一天」生成的基线 ⇒ **绕过 ≥5 门槛** ⇒ 该行 `manual_generated = true`
⇒ `Usable()` 判据改成：`sample_count >= MinForecastSamples || manual_generated`。

### 2.3 「有完整数据的一天」的校验（生成基线的前置）

那一天必须**同时**有：
1. **录入**：当天进了猪（`whole_pigs` 有当天进场的猪）；
2. **搬台**：当天有搬台流水 —— **含 0 kg 的「今天不搬台」标记也算**；
3. **销售**：当天有销售（零售或统收，至少一条流水）；
4. **盘点**：当天有**完整**盘点单（`is_complete = true`）。

⇒ 缺哪一项，400 里**点名缺哪一项**（门店才知道要补什么）。

### 2.4 跨店选用（整店 + 分层覆盖）

- 配置表 `pig_forecast_baseline_borrows`（已建）：
  `branch_id`(借用方) / `weight_band` / `cut_type` / `source_branch_id`(被借方) / `enabled`。
- **空 `weight_band` + 空 `cut_type` = 整店借用**；指定 `weight_band` = 该体重段全部部位；
  两者都指定 = 精确分层。
- **优先级**：精确 > 按体重段 > 整店；同级多个 ⇒ 取被借店**样本最多**的那个（确定性）。
- **效果**：重算基线时，本店该分层**自己的样本不够用**（`!Usable()`）⇒
  采用被借店那一行（同 band + cut）的数字 ⇒ 本店该行的 `source_branch_id` = 被借店。
- 被借店那一行自己也不可用 ⇒ 不借用（回退 LLM）。

### 2.5 多门店分级基线对比（#1）

按 `(体重段, 部位)` 分组，把多家店的基线并排 ⇒ 看哪家店的出肉率偏。
- 只读；需要请求的**每一个**门店都有 `freshmeat:view` 才能查。

## 3. API 契约（前端与契约测试按这份实现）

### 3.1 基线

```
GET    /forecast-baselines                      （已有；行新增 manual_generated / generated_from_date）
DELETE /forecast-baselines?weight_band=&cut_type=      删除不准确/脏基线（默认本店，可加 branch_id）
POST   /forecast-baselines/generate             按某一天生成（新增或覆盖）
POST   /forecast-baselines/recompute            （已有；整店重算，含借用解析）
GET    /forecast-baselines/compare?branches=00,01      多店对比
GET    /forecast-baseline-borrows               借用配置列表
POST   /forecast-baseline-borrows               新增/更新借用配置
DELETE /forecast-baseline-borrows/:id           删除借用配置
```

`POST /forecast-baselines/generate` 入参：

```json
{ "date": "2026-10-29", "source_branch_id": "", "overwrite": true }
```

- `date`：用哪一天的数据（**那一天必须数据完整**，见 §2.3）。
- `source_branch_id`：空 = 本店；非空 = 用**别店那一天**的数据生成到**本店的基线表**
  （= 手动跨店选用，`source_branch_id` 记被借方）。
- `overwrite`：true = 新增或覆盖；false = 只新增（已有分层不动）。

返回：

```json
{ "date": "2026-10-29", "source_branch_id": "00", "written": 30, "skipped": 0, "baselines": [ ... ] }
```

`GET /forecast-baselines/compare?branches=00,01` 返回：

```json
{
  "branches": ["00", "01"],
  "buckets": [
    {
      "weight_band": "200-249",
      "cut_type": "belly",
      "baselines": [
        { "branch_id": "00", "sample_count": 2, "p50_kg": "10.000", "p10_kg": "8.000",
          "p90_kg": "12.000", "sample_source": "estimated", "source_branch_id": "00",
          "manual_generated": false, "usable": false }
      ],
      "min_p50_kg": "10.000", "max_p50_kg": "12.000", "avg_p50_kg": "11.000",
      "spread_pct": 20.0
    }
  ]
}
```
