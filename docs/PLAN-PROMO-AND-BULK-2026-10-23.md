# 猪肉特价 SKU 智能分摊 + 板油(大宗)进销存 —— 方案(v2)

> 目标:让**整猪毛利**与**部位毛利**尽可能准确。
> 状态:v2 —— 已吸收 2026-10-23 的 4 项决策;**特价部分改为"日终智能分摊",取消人工按日指定**。
>
> 数据基础:直查两个生产源库(只读),窗口 = 近 14 个完整营业日(2026-10-09 ~ 10-22);
> 并通读了现有毛利算法 `internal/fresh-meat/service/gross_margin.go` 与
> `stocktake_calc.go`、`subscribe.go`。

## 0. 结论先行

毛利准不准,由四件事决定:

1. **收入完整** —— 每笔销售的金额+重量都进来了吗?
2. **重量闭合** —— 猪的 kg = 卖出 + 结存 + 损耗 + 在途/已结算的大宗?
3. **成本摊得到** —— 猪的成本按**正确的基数**摊到了卖掉的 kg 上?
4. **归属正确** —— 收入与重量归到了正确的部位、正确的猪?

现状这四条**各有一个洞**(§1)。方案三块:

| 块 | 内容 | 优先级 |
|---|---|---|
| **A 口径修正** | 成本分摊基数、实盘累加、成本对账行 | **P0**(独立可用,单独就能让报表变对) |
| **B 特价智能分摊** | 特价货号自动发现 + **日终按证据分摊**,取消人工按日指定 | **P0** |
| **C 板油大宗台账** | 产出录入 → 结算 → 回写毛利 | **P1** |

## 1. 现状诊断:毛利不准的 5 个具体原因

### ① 特价 SKU 的销售**整行被丢弃**(收入与重量同时丢)

`OnSaleCompleted` → `resolvePigByCubeProduct` 按 `(branch, cube_product_id)` 查
`branch_cut_mappings`;查不到 ⇒ `return "", "", nil` ⇒ 调用方 `continue` ⇒ **整行不落库**。

**好消息**:POS 事件里本来就带着 `sku_id / qty / amount` —— 数据一直送到了,
只是被"查不到映射就丢行"这条逻辑丢在门口。
⇒ **不需要新的数据管道**,只要在解析处加一个分支,特价的 kg/金额立刻就有。

⇒ 佳乐实测影响:**金额 ~5%(3257 元 / 65311 元)、重量 ~10%(440 斤 / 约 4300 斤)**。
重量比金额严重 ⇒ `expected_kg` 虚高 + 成本摊销比例 `min(1, sold/purchased)` 偏小 ⇒ 双重失真。

### ② 板油等大宗产出**没有收入通道**(有成本没收入)

板油由猪分割产生 ⇒ 成本摊给了这头猪;但走酒店/统购、几天后才结算出单价
⇒ 系统里**没有对应的收入行** ⇒ 这部分 kg 的毛利恒等于 `-100%`,重量永远挂在结存里。

### ③ 成本分摊基数**只用 LLM advice** ⇒ LLM 不可用时整猪成本完全摊不出去 ⚠️ 最严重

```go
// gross_margin.go
pigTotalInByID[p.ID] = Σ llmByPig[p.ID][c].ExpectedKg   // ← 只累加 LLM
...
if pigTotal.IsZero() { continue }                        // ← 该猪成本 → 0
```

生产上 `defaultPredictFn` = `history_avg`,**history 为空时返回 `cuts: []`**
⇒ `llmByPig[pig.ID]` 为空 ⇒ 基数 0 ⇒ `continue`
⇒ **这头猪的 purchase_cost 一分钱都没摊给任何部位** ⇒ 毛利被**大幅高估**。

### ④ 猪身上没被任何部位覆盖的 kg,**成本也摊不出去**

分摊基数 = LLM 给的 cut 之和,而它不含血、内脏、修割损耗、称重误差;
其和也 ≠ `gross_weight_kg` ⇒ 差额(通常 10~20%)的成本凭空消失 ⇒ 高估。
**板油正好属于这一类"产出但没进零售部位"的 kg** ⇒ ②和④是同一个洞的两面。

### ⑤ 实盘剩余按 cut **覆盖**而不是**累加**

```go
// gross_margin.go(当日实盘)
actualPerCut[sn.CutType] = sn.ActualRemainKg           // ← 覆盖!

// stocktake_calc.go(期初)
out[s.CutType] = out[s.CutType].Add(s.ActualRemainKg)  // ← 累加
```

同一件事两处口径相反。**一个部位挂多个 SKU 时**(上一轮刚改成允许),
当日实盘只保留最后一个 SKU 的重量 ⇒ 实盘剩余与差异(variance)全错。

## 3. B 块:特价智能分摊(替代人工登记)

### 3.1 核心思想

**用"账面缺口"定位特价来自哪个部位。**

当日某部位 c:

```
应产出 expected_c = Σ(pig_cuts.kg for c) + Σ(LLM 兜底 kg for c)
正常销量 sold_c    = 当日该部位**常规 SKU**的销量 kg(不含特价)
日终剩余 remain_c  = 当日 is_complete=true 盘点的剩余 kg(该部位所有 SKU 求和)
已记报损 waste_c   = 当日 waste_logs 的报损 kg

缺口 gap_c = expected_c − sold_c − remain_c − waste_c
```

`gap_c > 0` 的含义:**这个部位"少了这么多 kg 没被正常卖掉"** —— 它要么被特价处理了,
要么有未记录的损耗。⇒ **特价 kg 就藏在缺口里。**

> 例:当日两头猪应分割出后腿肉 30 斤,正常销量 20 斤,日终盘点剩 2 斤,无报损
> ⇒ `gap_后腿 = 30 − 20 − 2 = 8` ⇒ 这 8 斤就是被特价处理掉的。

**多部位同时有缺口时**(用户原思路):剩余越多的部位越可能滞销 ⇒ 更可能被拿去做特价。
但见 §6.2 —— 这条要**归一化后作为次要因子**,不能当主因子。

### 3.2 算法(日终,纯读路径)

```
Step 0  前置:当日必须有 is_complete=true 的盘点(硬依赖,见 §6.4)
        否则 → 不分摊,毛利标"特价未分摊(N 元)"并给出金额

Step 1  算缺口
        gap_c = expected_c − sold_c − remain_c − waste_c
        候选集 C = { c : gap_c > 0 }

Step 2  算权重(两因子)
        因子1 缺口占比     f1_c = gap_c / Σ_{c∈C} gap_c
        因子2 滞销度       turnover_c = remain_c / max(近30天日均销量_c, ε)
                            f2_c = turnover_c / Σ_{c∈C} turnover_c
        (无历史销量的部位回退:turnover_c = remain_c / max(expected_c, ε))
        权重   w_c = f1_c^α × f2_c^(1−α)        α 默认 0.7(偏重缺口)
        候选集为空 → 回退:f2_c 单独作权重(§6.3)

Step 3  用**实测**特价总量归一(关键:总量不用缺口!)
        K = Σ 特价销售行.kg         (从 POS 拿到,实测)
        R = Σ 特价销售行.amount     (实测)
        promo_kg_c     = K × w_c
        promo_amount_c = R × w_c     (等价于按 kg 加权平均单价 ⇒ 各档不同价不丢)

Step 4  残差处理
        若 Σ promo_kg_c 与 K 有差(取整/权重舍入)→ 差额进"未分摊残差"行,显式列出

Step 5  输出分摊明细(进毛利报告,见 §5.3)
```

**为什么总量必须用实测 K 而不是缺口 Σgap**:
缺口里混着未记录损耗、切分损耗、称重误差、盘点误差。
**用缺口当总量 ⇒ 把损耗算成了特价收入 ⇒ 毛利被高估。**
⇒ 缺口只用来定**比例**,总量永远取实测。

### 3.3 特价货号怎么识别(唯一还需要人工的地方)

**不做"人工按日指定部位",但仍需要一次性知道"哪些货号是特价"** ——
否则系统拿不到 K 和 R,分摊就没有总量。

**降摩擦的做法:系统自动发现 + 一次确认**
```
每日自动扫描:
  候选 = 当日有销量
       且 不在 branch_cut_mappings(还没被当成常规部位)
       且 出现在该店的**猪肉类目**(佳乐 1201 / 富百家 010303)下
       且 单位是重量单位(kg/斤/500g) —— 排除包/份/只的预制菜
后台弹清单:"这 5 个货号今天共卖了 440 斤 / 3257 元,标记为特价?"
→ 勾选确认 → 落 promo_skus(带生效日期)
```
之后**零维护**(候选清单为空时不需要任何操作)。
新增促销货号时才会再出现一次 —— 一年可能几次。

**为什么不靠"名字含特价"自动识别**:实测 佳乐 有 `00070 特价猪肉`、`03687 特价猪肉`、
`03001 特价猪肉5元`…… 名字里带"特价";但 `03390 特价猪肉5Y`、`00269 特价猪肉` 也带,
可也有 `00059 特价骨头A`。⇒ 名字特征**不完整**,必须靠"未映射 + 有销量"这种结构性证据。

### 3.4 新增枚举值 `promo`(34 → 35)

它是**商品类别**(促销档)而非解剖部位 ⇒ 与 `local_pork` 一样**不进整猪分割推演**。

## 4. C 块:板油大宗台账(按 Q1/Q2/Q3)

**通用化**:不只板油,凡"分割产生、零售不卖、攒几天统一结算"的都走这套
(板油 / 猪血 / 整根猪肠 …),`product_code` 区分。

### C1 主数据
```
bulk_products(id, branch_id, code, name, unit, active, note)
```

### C2 当日产出录入(= Q1:录"要进大宗的余量")
```
bulk_productions(
  id, branch_id, product_code, biz_date, qty_kg,     -- 扣掉零售后的余量
  allocation_mode,                                    -- pro_rata(按 Q2)
  operator_id, note, created_at
)
UNIQUE(branch_id, product_code, biz_date)
```
- **录入只要三样**:日期、品项、余量。
- 猪归属在**计算时**做:按当日各猪 `gross_weight_kg` 比例分摊(板油产量与猪的重量正相关)。
- **与零售互斥**:台账的 kg 是"没零售掉的那部分" ⇒ 零售的 00032/01445 走 POS,两边不重叠。

### C3 结算单(= Q3:交付离店)
```
bulk_settlements(
  id, branch_id, product_code,
  from_date, to_date,                 -- 结算覆盖的产出期间
  qty_kg, unit_price_yuan, amount_yuan,
  counterparty,                       -- 酒店/收购方
  settled_at, operator_id, note
)
```

### C4 FIFO 分配
```
bulk_settlement_allocations(
  id, settlement_id, production_id,
  qty_kg, amount_yuan, pig_id, production_date
)
```
结算时 FIFO 把结算量吃进未结的产出记录;按各产出记录贡献的 kg 分摊金额。

### C5 结算 ⇒ 回写毛利(复用现有引擎,不改毛利算法)
每条 allocation 写一行:
```
line_sales_by_pigs(
  branch_id, sale_date = production_date,   -- ★ 记在**产出日**
  pig_id, cut_type = "fat",
  qty_kg = 该猪贡献的 kg, amount_yuan = 分摊到的金额,
  unit_price_yuan = 结算单价,
  source = "bulk",
  pos_line_id = "BULK-<settlement_id>-<pig_id>"    -- 幂等键
)
```
> ★ **记在产出日而非结算日**:
> - 产出日就写 ⇒ 猪当天拿到它的板油收入 ⇒ **单猪毛利在正确的日子闭合**;
> - kg 平衡在产出日闭合(purchased=X, sold=X)⇒ 不留"永远挂着"的虚高库存;
> - 代价:结算是**事后回填**(改写历史某天)⇒ 报告要显式标"含事后结算回填";
> - 这就是标准的**权责发生制 + 事后定价**。

### C6 结存查询
```
某日某店某品项结存 = Σ bulk_productions(≤当日) − Σ bulk_settlement_allocations(≤当日)
GET /bulk-stock/balance?branch=&product_code=&date=
```

### C7 大宗与部位 kg 不重叠(设计要点)
- `fat` 部位行:purchased 只含**零售部分**的 pig_cuts,sold 只含 POS 零售销量,remain 只含盘点零售剩余;
- 大宗那部分**不写 pig_cuts**,而是走台账 + §5.1 的"分摊基数里加大宗量";
- ⇒ 两边干净不重叠,而**猪的总 kg 与总成本仍然闭合**(§5.1 保证)。

## 5. A 块:口径修正 + 两条配套

### 5.1 A1 分摊基数改用 `gross_weight_kg`,残差显式化 ⚠️

| 编号 | 改动 | 目的 |
|---|---|---|
| A1 | 成本分摊基数 = **`gross_weight_kg`**;各部位占比用 `入库kg / 入库总量`;**差额进显式的"未分摊残差"桶** | 猪的 kg 与成本完全闭合;LLM 不可用时不再整头猪成本归零(③④) |
| A2 | `actualPerCut` 改累加,与 `loadOpeningPerCut` 对齐 | 实盘剩余/差异正确(⑤) |
| A3 | 毛利报告加**成本对账行**:`Σ 各部位摊销成本 == Σ 当日猪 purchase_cost`(误差须 0) | **整猪毛利准不准,一眼可判** |
| A4 | 加 `unallocated` 残差桶的展示 | 看见"有多少 kg 没进任何部位"(通常就是血/修割损耗/称重误差) |

> **分摊基数里要加上大宗产出量**(§4-C7):大宗那部分 kg 已知且可归属到猪,
> 不该落进"残差"桶,而该有自己的成本。
> ⇒ 基数 = `gross_weight_kg`,分母口径与"该猪实际去向"一致,残差 = 真正说不清的部分。

### 5.2 二次分摊到单猪(建议做,几乎零成本)

§3 的分摊是**店级**的(按部位的缺口/剩余)。要落到单猪,再做一次:
```
对部位 c:该部位分到的 promo_kg_c,按当日各猪**在该部位的入库 kg**比例再分
⇒ 每头猪得到自己的 promo_kg / promo_amount ⇒ 整猪毛利才有意义
```
> Q2 选的是"**录入**不指定猪",不等于"**计算**不落到猪"。这一步是白送的,
> 不做的话单猪毛利只能到店级。

### 5.3 分摊明细随毛利报告一起出(你说的"详细调整说明")
```
gross_margin_report.promo_allocation = {
  "promo_kg_total": 440.8, "promo_amount_total": 3257.20,
  "basis": "gap_turned_over_weighted", "alpha": 0.7,
  "weights": [
    {"cut":"belly","gap_kg":5.2,"remain_kg":12.0,"turnover_days":3.1,"weight":0.62},
    {"cut":"leg_rear","gap_kg":2.1,"remain_kg":4.0,"turnover_days":0.9,"weight":0.31},
    ...
  ],
  "allocations": [
    {"cut":"belly","promo_kg":273.3,"promo_amount":2019.5},
    ...
  ],
  "residual_kg": 0.0,
  "note": "按当日 应产出−销量−盘点剩余−报损 的缺口加权(α=0.7),并以近30天日均销量算的周转天数作次要因子;总量取 POS 实测特价销量。",
  "is_estimated": true
}
```
每个部位行另带:
```
"revenue_yuan"            // 合计(实测 + 分摊)
"revenue_measured_yuan"   // 实测部分
"revenue_allocated_yuan"  // 分摊部分
"promo_kg"                // 分摊到的特价 kg
"data_source"             // actual | partial | estimated
```
⇒ **实测与推算在报表里分开**,不会出现"看不出哪部分是估的"。

## 6. 隐患清单(分三档)

### 6.1 必须处理(不改就会错)

| # | 隐患 | 处理 |
|---|---|---|
| H1 | **缺口 ≠ 特价**:缺口里混着未记录损耗/切分损耗/称重误差/盘点误差 | **总量用实测 K/R,缺口只定比例**(§3.2 Step 3)。绝不用 Σgap 当总量。 |
| H2 | **总价货号不识别 ⇒ 拿不到 K/R ⇒ 分摊无总量** | 系统自动列候选 + 一次确认(§3.3)。这是全流程唯一的"人工",而且是一次性的。 |
| H3 | **分摊结果若落回销售表 ⇒ 自反馈**(下一轮把分摊结果当输入) | 分摊**只发生在读路径**(毛利计算时现算),**不写回** `line_sales_by_pigs` 的正常销量行。 |
| H4 | **成本分摊基数漏掉未覆盖 kg** ⇒ 毛利高估 | A1(§5.1):基数改 `gross_weight`,残差显式化;配 A3 对账行。 |

### 6.2 需要修正你的原思路(隐患在"剩余较多"这条)

| # | 隐患 | 说明 |
|---|---|---|
| H5 | **"剩余多"会选错部位** | 物理上,特价来自**缺口大**的部位(它"少了 kg");而"剩余多"是**间接**信号,且**大部位天然剩余多** ⇒ 不归一化就是按体量分配,不是按滞销分配。<br>**反例**:后腿 应产出30/销量20/剩余2 ⇒ gap 8;五花 应产出50/销量40/剩余12 ⇒ gap −2(LLM 低估)。真相是后腿特价,但"剩余多"会把 8 斤全给五花。<br>⇒ **修正:缺口为主因子(α=0.7),滞销度为次因子且必须用周转天数归一化**(§3.2 Step 2)。 |
| H6 | **LLM 高估会让真凶的缺口变负** ⇒ 该部位被踢出候选 ⇒ 分摊到错误部位 | `expected_c` 优先用 `pig_cuts` 实际值;候选集为空时回退到滞销度单因子;**并在报告里标出"最大不确定度"**(权重与缺口背离最大的部位)。<br>⇒ 这也反过来说明:**推动"单品补录(pig_cuts)"的录入率**是分摊精度的前提。 |
| H7 | **分摊是推算,不是实测** | 报表里 `revenue_measured` / `revenue_allocated` 分列 + `is_estimated` 标记(§5.3)。 |

### 6.3 需要接受 / 需要防御

| # | 隐患 | 说明与对策 |
|---|---|---|
| H8 | **硬依赖 `is_complete=true` 的盘点** | 没有盘点 ⇒ `remain_c` 未知 ⇒ 缺口算不出 ⇒ **完全分不了**。降级:不分摊 + 显式标注"特价未分摊 N 元"(金额仍在总账里)。 |
| H9 | **分摊精度随 `pig_cuts` 录入率波动** | `expected_c` 越依赖 LLM,缺口越不准 ⇒ 分摊越不准。报告里给出"本日录入率"作为置信度指标。 |
| H10 | **多猪交叉**:一头猪的五花和另一头猪的后腿同时特价,店级比例会混着分 | 二次分摊(§5.2)能缓解 —— 按"该部位各猪的入库 kg"比例分,而不是按猪数均分。 |
| H11 | **盘中毛利必然不准** | 日终盘点前没有 `remain_c` ⇒ 分摊做不了。⇒ 盘中毛利:特价金额归 `promo` 桶,报表顶部显式提示"**特价未分摊,当前毛利为未完成口径**"。 |
| H12 | **特价各档不同价**(8元/20元/斤) | 分摊金额按权重切分(= kg 加权平均单价)⇒ 各档的价格被保留,不会按均价摊平(§3.2 Step 3)。 |

## 7. 实施顺序与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0-1** | A1~A4 口径修正 | ①成本对账行误差恒为 0;②LLM 不可用时整猪成本不再归零(单测:空 advice + 有 pig_cuts ⇒ 成本照摊);③当日实盘与期初口径一致(多 SKU 求和) |
| **P0-2** | B: 特价货号自动发现 + 识别分支 + `promo` 枚举 | ①特价销售行**不再被丢弃**(契约测试);②毛利报告出现"特价未分摊"金额,与源库对账一致 |
| **P0-3** | B: 日终智能分摊 + 分摊明细 | ①分摊后各部位 promo kg 之和 == 实测特价 kg;②分摊明细含权重/依据;③候选集为空、盘点缺失等降级路径都有明确输出 |
| **P0-4** | B: 二次分摊到单猪 + 毛利报告字段(measured/allocated) | 单猪毛利含分摊收入;总账仍闭合 |
| **P1** | C1~C7 大宗台账 | ①录入余量 → 结存可见;②结算 → 对应猪毛利出现该笔收入;③成本对账行仍为 0;④零售与大宗 kg 不重复 |
| **P2** | Flutter 前端(特价候选清单 / 分摊明细 / 大宗台账)+ deployer 契约测试 + 部署 | 三仓测试全绿 + 生产部署 + 契约测试打生产 |

> P0-1 独立可用:即使特价还没分摊,光修口径就能让报表方向变对
> (它修的是"整猪成本摊不出去"这个**系统性高估**,与特价造成的低估方向相反)。
